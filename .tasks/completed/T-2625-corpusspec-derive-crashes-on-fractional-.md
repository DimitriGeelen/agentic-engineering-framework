# T-2625: corpus_spec derive crashes on fractional lane height (editor-saved floats)

## Context

`fw corpus derive draft-trigger-handling` crashes with `ValueError: invalid literal for int() with base 10: '323.91686531856146'` at `tools/corpus_spec.py:189` — the lane-height parser coerces with `int()`, but the designer editor legitimately saves fractional lane heights (operator's v2 layout pass on the pair-draft resized the Human lane by drag). Node positions already parse as `float()` (line 211); lane height is the one integer-assuming holdout. Discovered live during the T-2620/arc-014 pair-draft round 2. Fix must not change emitted bytes for existing integer-height maps (prove/identity contract requires byte-identical regeneration).

## RCA

**Symptom:** `fw corpus derive draft-trigger-handling` crashed with `ValueError: invalid literal for int() with base 10: '323.91686531856146'` — first derive of a map after an operator drag-edited lane sizes in the designer UI (arc-014 pair-draft round 2).

**Root cause:** `parse_map` coerced `laneMeta height` with `int()` while node positions already used `float()` — an integer assumption baked in when all corpus maps were agent-generated with round integer heights. BPMN DI dimensions are floats by spec; the editor's drag-resize produces full-precision fractions.

**Why structurally allowed:** every prior map in the store was generated (never hand-resized), so the fractional case had zero coverage — the derive path had only ever seen its own generator's output. The pair-draft loop is the first workflow where editor-authored bytes flow back through derive.

**Prevention:** regression test `test_fractional_lane_height_round_trips_and_integer_stays_bare` in `tests/unit/test_corpus_spec_roundtrip.py` pins both the fractional parse and the integer byte-stability; the draft-trigger-handling map itself (fractional height in-store) now exercises the path on every corpus-wide derive/lint sweep.
