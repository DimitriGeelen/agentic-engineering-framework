# T-3360: branch-hygiene has no ahead-of-remote rail: 32 commits stranded 3 days with every handover reporting success

## Context

`lib/branch-hygiene.sh` measures branches **behind** their target
(`behind-threshold`, `diverged-fork`, both keyed on `FW_BRANCH_BEHIND_WARN`). It
has no rail for the opposite direction — a branch that is **ahead of its remote
and not pushed**.

That is the direction that actually strands work. Measured 2026-09-07..10:
`origin/bleeding-edge` last received a commit on 09-07 23:06, and the pre-push
audit gate then refused every push for ~3 days while the branch climbed to 32
commits ahead (OBS-394/395, root cause fixed in T-3357). Throughout, every
session-end handover ran, committed, and reported success — the push failure was
visible only in the tail of the handover's own stdout. Nothing watched the gap, so
"handover succeeded" and "three days of work is stranded locally" printed
identically.

This is the same false-signal family as the rest of the cluster, one level up: the
*session-end protocol* reports success while its last act silently fails.

**Design note — why commits-ahead plus commit age, and not "time since last
push".** Git records no reliable last-push timestamp; the closest proxy is the
remote-tracking ref's reflog, which is absent on fresh clones and prunable. The
age of the **oldest unpushed commit** answers the same question ("how long has
this been stranded?") from committed data that is always present. So the finding
carries both the count and the stranding duration.

## RCA

**Symptom.** 32 commits sat unpushed on `bleeding-edge` for ~3 days. No surface
reported it. Every session-end handover in that window ran, committed, and
reported success.

**5 Whys.**

1. *Why were the commits stranded?* The pre-push audit gate refused every push
   (root cause fixed in T-3357).
2. *Why did nobody notice the refusal?* It appeared only in the tail of the
   handover's own stdout, which nothing reads after the fact.
3. *Why did no health surface catch the backlog?* `fw doctor` and `fw audit` both
   read `fw_branch_hygiene`, and every rail in it measures a branch **behind** its
   target. None measured **ahead**.
4. *Why only behind?* The rails were built (T-100142/3/4, T-3094, T-3187) to find
   branches that had fallen out of date and needed reconciling. "Work that exists
   only locally" is a different question, and nobody had asked it.
5. *Why is that the dangerous half?* A branch that is behind is recoverable at any
   time — the commits are safely on the remote. A branch that is ahead holds the
   only copy. The rails covered the direction where nothing is at risk and left
   the direction where everything is.

**Root cause.** A monitoring surface whose finding classes were derived from the
failures already seen, rather than from where the value actually sits. Behind-ness
is visible (the branch looks out of date); ahead-ness looks identical to healthy
work-in-progress until the moment it is lost.

**Structural change (prevention, not mitigation).** `ahead-unpushed` fires on the
dev branch past a registered threshold and reports the **stranding duration**, not
just the count. Scoped to stay silent with no upstream, at/under threshold, and
WARN-only. Verified live on the origin condition: `ahead-unpushed bleeding-edge
ahead=36 oldest_days=3 (threshold 20)`, surfaced first among 19 findings in
`fw doctor`. Mutation-verified: four assertions go red when the rail is made
unreachable, while the silence-controls and the sibling behind-rails stay green.

**Method note.** Two test defects were caught by checking rather than trusting
green: a fixture helper that reused filenames (so a second batch of commits
silently added nothing), and a display-cap assertion whose premise was
unsatisfiable (cap 2 with 3 classes must drop one — correct behaviour, wrong
test). The cap test now runs at the production cap with a binding control.

**Not fixed here.** "Time since last push" as a separate signal — git records no
reliable push timestamp, and oldest-unpushed-commit age answers the same question
from data that is always present. Noted rather than silently omitted.
