# T-5123: fw termlink check crashes with unbound hub_dir when no hub is reachable

## Context

**Background / trigger:** session S-2026-1113-1845 (resumed 2026-11-13) ran
`bin/fw termlink check` while diagnosing why the handover's suggested first action
(the T-5054 adapter trial) could not reach the sidecar. The command printed its first
two OK lines and then died:
`agents/termlink/termlink.sh: line 392: hub_dir: unbound variable`.

**Problem / hypothesis:** `agents/termlink/termlink.sh:382` declares
`local hub_pid hub_dir cfg_dir` without initialising them. `hub_dir` is assigned only
inside `if [ -n "$hub_pid" ] && [ -r /proc/$hub_pid/environ ]` (384-386). When no hub
process is found — or its environ is unreadable — `hub_dir` stays *declared but unset*,
and the script runs under `set -u`, so the first dereference at 391/392
(`[ -n "$hub_dir" ]`) aborts the function. The crash therefore fires exactly when no hub
is reachable, which is precisely when an agent runs this command to find out why.

**Goal:** `fw termlink check` completes its full report whether or not a hub is
reachable, and says which it found.

**Expected outcome:** running `bin/fw termlink check` on a host with no reachable hub
prints every check it is supposed to print and exits without an unbound-variable abort.

**Symptom:** `bin/fw termlink check` printed its first three lines and aborted with
`agents/termlink/termlink.sh: line 392: hub_dir: unbound variable`. The remaining
checks never ran.

**Root cause:** `_check_hub_store_parity` declared `local hub_pid hub_dir cfg_dir`.
In bash a bare `local x` leaves `x` **unset**, not empty. `hub_dir` is assigned only
inside `if [ -n "$hub_pid" ] && [ -r "/proc/$hub_pid/environ" ]`, so when no hub
process is found — or its `environ` is unreadable, which is the case for a root-owned
hub read by a non-root session — it stays unset. The function runs under
`set -euo pipefail`, so the first `[ -n "$hub_dir" ]` aborted it.

**Why structurally allowed:** the function has two paths and only one was ever
exercised. On the development host a hub is normally running and readable, so
`hub_dir` is always assigned and the unset branch is unreachable. There was no test
for the no-hub case, and nothing in the suite runs `termlink check` against a host
without a hub. `shellcheck` does not flag a declared-but-unset local, and the
suite's tripwire makes the real binary return no version, so any naive test of this
command returns early at line 420 and never reaches the branch at all — a green that
proves nothing. That last point was reproduced here: the first draft of
`tests/unit/t5123_termlink_check_no_hub.bats` passed its subject leg while
exercising none of the code under test, and was only caught because the control leg
failed.

**Prevention:** `tests/unit/t5123_termlink_check_no_hub.bats` pins the no-hub path
with three legs — the subject (the real script completes), a **control** (the same
script with the initialisers stripped reproduces the abort, so a pass proves the test
can still see the bug), and a source assertion. The subject leg asserts *positive
evidence* that the bug site was reached (the T-3424 WARN emitted in the same
branch), not merely the absence of the abort; without that assertion the test is
satisfied by an early return. The test stubs `pgrep` to exit 0 with no output — a
non-zero exit aborts the `hub_pid=$(…)` assignment under `errexit` before the bug
site — and stubs `termlink` ahead of the suite tripwire, contacting nothing.

**Found because the crash hid the answer:** the command was being run to diagnose why
this session could not reach TermLink. With the abort removed it immediately reported
`agent-chat-arc is NOT on the store the CLI resolves` — the actual finding, which the
crash had been masking.
