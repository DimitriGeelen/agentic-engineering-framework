# T-3376: Resolve OneDev push credential via Ring20 Manager credentials service — unblock 91 stranded commits (OBS-395/OBS-106)

## Context

91 commits sit unpushed on `bleeding-edge`; `origin` last received a commit
2026-09-07. `git push` fails with `remote: You do not have permission to push to
this project` → `fatal: Authentication failed`.

Operator direction: *"Please work with Ring20 Manager for the credentials. We have
a service for that."* Ring20 Manager is at **192.168.10.122** — hub reachable at
`192.168.10.122:9100`, session `ring20-management-agent` (role=manager,
concierge=ring20).

**Working hypothesis (not yet confirmed):** OBS-106 records that the OneDev origin
URL embeds an auth token verbatim, that the token is committed in the tracked tree
at `.agentic-framework/.upstream`, and that this repo is mirrored to a PUBLIC
GitHub remote — so we recommended rotating it. If that rotation happened, a stale
token still sitting in `remote.origin.url` produces exactly this symptom. That is a
hypothesis with a clear test, not a conclusion.

**Standing constraint carried into this task.** Whatever credential arrives must
NOT be embedded in `remote.origin.url` and must NOT land anywhere in the working
tree. Doing so is the precise mechanism that created OBS-106 — a live credential
committed and then published to a public mirror. Fixing the push by re-creating
that exposure would be a net loss.

**Sovereign boundary already hit.** The local credentials service refused:
`CREDENTIAL GATE: Access denied for 'infisical.token' [CRITICAL]` — per-request OTP
delivered by ntfy, *"Tier 0 (CRITICAL) cannot be session pre-approved"*. Only the
operator receives that OTP. I cannot self-serve, and will not attempt to.

## Findings so far (PARKED — budget gate at 292,219 tokens / ~97%)

**1. Ring20 Manager is reachable and has been asked.** Hub `192.168.10.122:9100`
responded in 129ms with three sessions: `ring20-management-agent`
(role=manager, concierge=ring20, tags `host=122 project=proxmox-ring20-management`),
`ring20-live-agent`, `skills-manager-agent`. A 1863-byte request was injected into
`ring20-management-agent` (`status: injected`). **No reply read yet** — the budget
gate fired before I could poll its PTY output. That is the first thing to pick up.

**2. The credentials service refuses me, by design.** `credentials_list` returned
exit 403: `CREDENTIAL GATE: Access denied for 'infisical.token' [CRITICAL]`,
per-request OTP delivered by ntfy, *"Tier 0 (CRITICAL) cannot be session
pre-approved — a per-request OTP is mandatory"*, 300s expiry. The request it
created (`REQ-20260916-204741-m16z`) has long since expired. **Not retried**, because
re-running only mints a fresh OTP that still only the operator receives; repeatedly
firing it would be pressuring a Tier-0 gate, not working with it.

**3. My stated hypothesis was WRONG, and the correction matters.** I expected a
stale token embedded in `remote.origin.url`. Measured:

```
remote.origin.url = https://onedev.docker.ring20.geelenandcompany.com/agentic-engineering-framework.git
```

**No embedded credential.** OBS-106 asserted the URL embedded a token that
"byte-matches the credential in the live remote.origin.url today" — so between that
filing and now, something stripped it. Either the operator acted on OBS-106, or a
rotation/cleanup ran.

**Revised hypothesis (untested):** the token was removed from the URL without a
credential helper being configured to supply it, so git now authenticates as nobody
— which matches the observed `permission to push` → `Authentication failed` pair
exactly. This is a *different* remedy from "rotate the token": it needs a helper
configured, not just a new secret.

**4. What I did NOT get to check** (budget gate stopped the command mid-flight — all
read-only, all cheap, all first things to run next):
- `git config --get-all credential.helper` — is any helper configured at all?
- whether `~/.git-credentials` exists, and its permissions
- whether `.agentic-framework/.upstream` **still** embeds a token (OBS-106 leg 2 —
  if the URL was cleaned but the vendored file was not, the credential is still
  committed and still publicly mirrored, which would be the more urgent finding)
- whether the OBS-394 pre-push audit gate is *also* shut, which no credential fixes

**5. Nothing was bypassed and no secret was handled.** No token was requested in
plaintext, none was printed, none was written anywhere. The request to Ring20
Manager explicitly asked it *not* to return a token inline and *not* to hand back a
URL with one embedded, naming OBS-106 as the reason.

# THE DEFAULT — redirect to a file, then grep the file:
#     cmd > /tmp/.out 2>&1 && grep -q "PATTERN" /tmp/.out
#     curl -sf "$(bin/fw watchtower url)/page" -o /tmp/.out && grep -q "PAT" /tmp/.out
# Correct at any output size, and `&&` keeps the PRODUCING command's exit code in
# the verdict. Reach for this first; the alternative below is the special case.
#
# Why not `cmd | grep -q PAT` (L-387): P-011 runs each line with PIPEFAIL LIVE
# (errexit is not — see below). When grep matches it exits and closes stdin while cmd is still
# writing, cmd takes SIGPIPE, the pipeline exits 141 — verification "fails" with
# the pattern present. Captured 4× (T-1716, T-1838, T-1862, T-1863).
#
# THE EXCEPTION — capture first, grep the capture:
#     out=$(cmd 2>&1); echo "$out" | grep -q "PATTERN"
# Valid ONLY while "$out" fits the 65536-byte pipe buffer, and it is on you to
# know that it does. Above that the form inverts and becomes the very failure
# L-387 describes: echo blocks on the full pipe, grep -q exits, echo takes
# SIGPIPE, rc=141 (T-2743 — measured on a 146,366-byte Watchtower page, 3/3 runs,
# deterministic not racy; rendered routes run 50-200KB, so anything that curls a
# page is over the line). It also discards cmd's exit code, so a 404 yields an
# empty capture that grep merely fails to match rather than a failed line.
# If you do use it: single pipe only, no intermediate tail/awk/sed stage between
# capture and grep (T-2090) — the middle stage is what `grep -q` slams its stdin
# on, and grep scans the whole captured string anyway, so the `tail -3` was
# cosmetic. `echo "$out" | grep -q PAT`, nothing between.
#
# TEST RUNNERS need a guard either way (T-2738). `set -e` is suppressed inside the
# `if` condition the gate runs each line in, so in `cmd1; cmd2` only cmd2 is the
# verdict — and the pass marker you grep for survives a partial failure: a suite

# to `grep -qE "[0-9]+ passed"` matches the same output. Keep the exit code:
#     python3 -m pytest <file> -q > /tmp/.out 2>&1 && grep -q passed /tmp/.out
