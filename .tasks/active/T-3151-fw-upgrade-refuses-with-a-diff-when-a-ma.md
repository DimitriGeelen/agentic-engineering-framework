# T-3151: fw upgrade refuses with a diff when a managed file is locally modified

## Context

<!-- One sentence for small tasks. Link to design docs for substantial ones. -->

## Acceptance Criteria

### Agent

- [ ] The refusal fires on SAME-VERSION runs. 001-CashWeb measured `Pinned: v1.6.29 (current)`
      — nothing to upgrade — and nine assertions still died, because the vendored tree is
      re-copied regardless. A no-op upgrade is the most dangerous shape precisely because it is
      the case where nobody thinks a check is needed.
- [ ] `fw upgrade` compares each managed file against the content it last wrote, and detects
      local modification by content — not mtime, and not `.framework.yaml version:`, which sat
      unchanged at 1.6.29 across all four losses in the origin report.
- [ ] On detection, upgrade exits non-zero and prints a unified diff of what it would destroy,
      naming the project-owned seam from T-3150 as the place that content belongs.
- [ ] The refusal is a refusal, not a prompt — it does not proceed on silence or on a
      non-interactive stdin.
- [ ] `FW_ALLOW_MANAGED_OVERWRITE=1` bypasses, and writes a Tier-2 entry to
      `.context/working/.gate-bypass-log.yaml`.
- [ ] `tests/unit/upgrade_refuse_modified.bats` covers refuse, bypass, and the clean path,
      including a control proving the fixture actually diverges (an identical file must NOT refuse).
