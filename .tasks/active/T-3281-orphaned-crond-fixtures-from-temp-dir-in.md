# T-3281: Orphaned cron.d fixtures from temp-dir installs starve the audit lock

## Context

Six `/etc/cron.d/agentic-audit-proj-schedule-install*` entries, left behind by
test-fixture installs, each declare a `PROJECT_ROOT` under `/tmp` that no longer
exists. All six invoke `/opt/999-Agentic-Engineering-Framework/bin/fw audit`, so
when `_project_root_is_stale()` rejects the vanished root, resolution falls through
to `FRAMEWORK_ROOT` and the jobs audit **this** repo instead of refusing. Twelve
extra audit invocations per hour land on `:00`/`:30` without the per-job
`/var/lock` flock the registry-generated entries carry, so they serialise on
`.context/locks/audit.lock` and hold it for minutes at a time. Every pre-push
audit gate then fails with "Another audit is already running — exiting (no verdict
produced)", which is what stranded handover `426e1524d` and cost this session
three push attempts.

The framework tracks three cron drift classes (registry→generated→deployed,
CLAUDE.md §Verification Gate). This is a **fourth**: deployed entries with no
registry behind them at all. Nothing looks for those, which is why six of them
accumulated unnoticed.

**Scope fence.** This task ships *detection* only — the `fw doctor` check plus the
remediation command it prints. Deliberately out of scope, filed separately:
the silent re-target in `bin/fw` PROJECT_ROOT resolution (the root cause), and a
sanctioned `fw cron` removal verb. `bin/fw` is vendored and another session is
live in this checkout; a resolution change there is not a same-session edit.

## RCA

**Symptom:** `fw handover --commit` and `git push` failed repeatedly with "Another
audit is already running — exiting (no verdict produced)". Handover commit
`426e1524d` sat unpushed across a compaction boundary; three further push attempts
lost the same race, one of them *after* waiting for the lock to clear — it was
retaken within seconds.

**Root cause:** six `/etc/cron.d/agentic-audit-proj-schedule-install*` entries from
temp-dir test-fixture installs declare `PROJECT_ROOT` paths under `/tmp` that no
longer exist. `bin/fw` correctly classifies the vanished root as stale, re-resolves,
finds no usable cwd (cron supplies none) and falls back to `FRAMEWORK_ROOT`. All six
therefore audit *this* repo. They fire at `:00`/`:30` without the per-job `/var/lock`
flock that registry-generated entries carry (T-1331/T-1558), so unlike the sanctioned
jobs they do not deduplicate each other, and twelve extra audits an hour queue on
`.context/locks/audit.lock`.

**Why structurally allowed:** two gaps, both registered as G-103.

1. The fallback to `FRAMEWORK_ROOT` is right for an interactive `fw` run from inside
   the framework repo and wrong for a cron job that *named* a project explicitly. An
   explicit `PROJECT_ROOT` that has vanished is a broken job, not an unspecified one.
   The mis-targeting is silent in both directions — the dead project gets no audit,
   the live one gets load it never asked for.
2. The framework tracks three cron drift classes along registry → generated →
   deployed. All three compare a project's own registry against its own deployed
   file, so none can see a deployed entry with *no registry behind it at all*. Six
   accumulated unnoticed. `fw cron` also has no removal verb, so even once found
   there was no sanctioned way to clear one.

The symptom named none of this. "Another audit is already running" is a true
statement about a lock, and points at cron nowhere — which is why the cost was paid
as repeated push failures rather than investigated.

**Prevention:** `fw doctor` now names each orphan, its dead root, and a
copy-pasteable removal command (`lib/cron-orphans.sh`, wired at `bin/fw:3437`,
pinned by `tests/unit/t3281_cron_orphan_scan.bats`). This is detection, not
prevention of creation — cause (1) above is untouched and G-103 stays open for it.
Stated plainly because the distinction is the point of G-019: the next orphan will
still be created, but it will be one `fw doctor` away from visible instead of
surfacing as an unexplained push failure days later.
