# T-3371: Fix lost-update race in hook telemetry counter (OBS-417)

## Context

The hook telemetry counter's read-modify-write was lock-free and lost ~99% of its
increments under concurrency (OBS-417). Found while running judge finding I1 during the
T-3370 value review: the counter was the instrument that raised a false alarm about
write-time gates not firing, and the alarm turned out to be the instrument's own damage.

## Resolution

**Root cause.** `_fw_telemetry_increment` did `mapfile` → edit array → `printf > file`
with no lock. Concurrent hooks both read, both write, and the last writer wins with its
own stale view — silently discarding every key it had not read.

**Fix.** Serialize the read-modify-write with `flock` on a `${file}.lock` fd, and split
the critical section into `_fw_telemetry_rmw`. The rewrite now also self-heals the two
corruption shapes the race left behind (blank lines; shadowed duplicate keys), taking the
**first** occurrence of a key rather than summing — summing would fold a stale corpse into
the live count and inflate it.

**Degrade-to-allow preserved (L-331).** No flock on the host, or lock not acquired within
`FW_TELEMETRY_LOCK_WAIT` (default 2s) → the increment proceeds unlocked. A lossy counter is
bad; a wedged hook is worse.

**Measured.**

| | before | after |
|---|---|---|
| 8 procs × 200 increments | sum **17**, 3 keys, 1 duplicate | sum **1600**, 8 keys, 0 duplicates |
| cost per fire | 632 µs | **2297 µs** (budget 5000 µs) |
| live `.hook-counter` | `budget-gate` twice (39 + stale 31) + blank line | single `budget-gate`, no duplicates, no blank line — healed on first fire |

**Bench-harness note.** The perf assertion runs in a plain `bash` subprocess, not inside
the `@test` body: bats installs a DEBUG trap that instruments every command and measured
the same code at ~88 ms/fire versus ~2.3 ms outside it. Timing it in place would have
measured the harness and reported it as the subject's cost.

**Found but NOT fixed here (one bug, one task):** `tests/unit/hook_telemetry.bats` test 14
(the T-1626 missing-hook witness) is RED — `bin/fw hook <missing>` warns, exits 0, and
records nothing. Confirmed pre-existing by git-stashing this change and re-running: it
fails identically on the unmodified file. Filed as **OBS-418**; it needs its own task.

# THE DEFAULT — redirect to a file, then grep the file:
#     cmd > /tmp/.out 2>&1 && grep -q "PATTERN" /tmp/.out
#     curl -sf "$(bin/fw watchtower url)/page" -o /tmp/.out && grep -q "PAT" /tmp/.out
# Correct at any output size, and `&&` keeps the PRODUCING command's exit code in
# the verdict. Reach for this first; the alternative below is the special case.
#
# Why not `cmd | grep -q PAT` (L-387): P-011 runs each line with PIPEFAIL LIVE
# (errexit is not — see below). When grep matches it exits and closes stdin while cmd is still
# writing, cmd takes SIGPIPE, the pipeline exits 141 — verification "fails" with
# the pattern present. Captured 4× (T-1716, T-1838, T-1862, T-1863).
#
# THE EXCEPTION — capture first, grep the capture:
#     out=$(cmd 2>&1); echo "$out" | grep -q "PATTERN"
# Valid ONLY while "$out" fits the 65536-byte pipe buffer, and it is on you to
# know that it does. Above that the form inverts and becomes the very failure
# L-387 describes: echo blocks on the full pipe, grep -q exits, echo takes
# SIGPIPE, rc=141 (T-2743 — measured on a 146,366-byte Watchtower page, 3/3 runs,
# deterministic not racy; rendered routes run 50-200KB, so anything that curls a
# page is over the line). It also discards cmd's exit code, so a 404 yields an
# empty capture that grep merely fails to match rather than a failed line.
# If you do use it: single pipe only, no intermediate tail/awk/sed stage between
# capture and grep (T-2090) — the middle stage is what `grep -q` slams its stdin
# on, and grep scans the whole captured string anyway, so the `tail -3` was
# cosmetic. `echo "$out" | grep -q PAT`, nothing between.
#
# TEST RUNNERS need a guard either way (T-2738). `set -e` is suppressed inside the
# `if` condition the gate runs each line in, so in `cmd1; cmd2` only cmd2 is the
# verdict — and the pass marker you grep for survives a partial failure: a suite
# printing "3 failed, 9 passed" satisfies `grep -q "9 passed"`, and generalising
# to `grep -qE "[0-9]+ passed"` matches the same output. Keep the exit code:
#     python3 -m pytest <file> -q > /tmp/.out 2>&1 && grep -q passed /tmp/.out
# or add the guard the exit code used to supply:
#     out=$(python3 -m pytest <file> -q 2>&1); echo "$out" | grep -q passed && ! echo "$out" | grep -q failed
