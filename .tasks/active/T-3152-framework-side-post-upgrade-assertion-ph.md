# T-3152: Framework-side post-upgrade assertion phase with consumer-supplied assertions

## Context

<!-- One sentence for small tasks. Link to design docs for substantial ones. -->

## Acceptance Criteria

### Agent

- [ ] The assertion runner ships in the framework (`lib/`), invoked by `fw upgrade` after the
      rewrite phase completes. It is not a consumer-registered hook.
- [ ] Consumer assertions are read from a path `fw upgrade` never writes
      (`.context/upgrade-assertions.yaml`), so the upgrade cannot delete its own check.
- [ ] A test proves the load-bearing property: **deleting the consumer's `CLAUDE.md` and
      `.claude/settings.json` does NOT disable the runner.** This is the whole reason the
      mechanism is framework-side rather than consumer-side.
- [ ] When the consumer supplies no assertions, a default set is derived from the files the
      upgrade **actually rewrote in that run** — not a static list, which would go stale the
      first time a new write site is added.
- [ ] Assertion failure exits non-zero and reports per-assertion pass/fail; an empty assertion
      set REFUSES rather than reporting success, per the T-3144 empty-scan rule (nothing was
      looked at is not nothing was wrong).
