# T-4916: Delegated deterministic [REVIEWER] criteria have no close path since T-4778 (delegate promises auto-tick; judge and ledger refuse them)

## Context

<!-- All four parts are required before source edits (T-4907). Plain language; link design docs for substantial tasks. -->
**Background / trigger:** ring20-dashboard (msg 616b90f3, 2026-10-29, their T-2585, on v1.8.15). Their operator chose to clear about 153 criteria that `fw task delegate` had converted from Human ACs to `[REVIEWER]` Agent criteria (owner human → agent). They found no way to close any of them:
- `fw reviewer T-765` (static scan): since T-4778 a PASS ticks only a criterion that names a scanner check, and theirs name none.
- `fw reviewer judge T-765 --dry-run` says "No REVIEWER_JUDGES criteria found".
- `lib/verdict_ledger.py` accepts a green verdict only for criteria that delegation routes to REVIEWER-JUDGES.

They will not edit prefixes by hand; they are collecting live Evidence blocks per criterion and ticking nothing.

**Problem / hypothesis:** confirmed by reading the code (2026-10-30). Two changes were each correct alone but left a dead end between them.
- `lib/delegation_cli.py:250` and `:523` still tell the user that a `fw reviewer` PASS auto-ticks the converted criteria (the T-1985 rail D-626 relied on).
- T-4778 narrowed auto-tick to named scanner checks, so converted deterministic criteria can never auto-tick.
- The scan then says "route to fw reviewer judge" (`lib/reviewer/static_scan.py:189`), but judge and the ledger only take REVIEWER-JUDGES criteria (taste, render-surface, unclassified, inception-decision).

So the operator's ruling D-626 ("agent can use the reviewer agent … and with a positive outcome close it") currently reaches nothing for the deterministic class, on 1.8.15 and on bleeding-edge alike. The agent ticking them itself would be self-certification of criteria the operator wrote, which is what delegation was meant to avoid.

**Goal:** a delegated deterministic criterion has one sanctioned close path. An independent reviewer checks the criterion against evidence (running its Steps where they are commands), and a recorded green verdict ticks it through the existing ledger and close gate. The text `fw task delegate` prints matches that path.

**Expected outcome:**
- `fw reviewer judge` plans and dispatches REVIEWER-CLOSEABLE (converted `[REVIEWER]`) criteria, not only REVIEWER-JUDGES ones.
- The verdict ledger accepts a green verdict for them with the same provenance rules, so `--status work-completed` ticks them with no `--skip-*`.
- Evidence blocks a consumer has already written are part of the brief.
- `fw task delegate` and the static scan name `fw reviewer judge` as the close path.
- Tests: a converted criterion closes on a green recorded verdict, and stays open on amber/red.
- ring20-dashboard is told.
- Design check before building: whether the class should simply be REVIEWER-JUDGES at conversion time (one class, one path) rather than teaching judge a second class.
- Design input from ring20-dashboard (msg 1cbe4ea5): many old criteria are dated (counts from May, a retired page, steps naming `bin/fw` where only `.agentic-framework/bin/fw` exists). Their Evidence blocks are dated and say HOLDS / PARTLY / CANNOT BE CHECKED NOW / DOES NOT HOLD. They ask that the reviewer judge the criterion's intent against the evidence, not the stale literal. Open question, not settled: green on "intent" would let a reviewer quietly rewrite an operator-written criterion. The safer shape may be that a stale-literal criterion gets amber or escalate, with the reviewer's proposed restatement, so the operator rules once on the restatement. Decide with the operator before building.
