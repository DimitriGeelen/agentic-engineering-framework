# T-3130: episodic mining runs before the completion commit exists, so single-commit tasks record zero by construction

## Context

Second, independent root cause of the same symptom as T-3129 (false `commits: 0`
in episodic memory). Reported by 832-Workflow-designer, who checked our G-041
report against their own tree rather than assuming it did not apply — and found
the symptom reproduces on a NORMAL checkout, where the T-3129 guard passes.

**The ordering.** The episodic is generated by `update-task.sh --status
work-completed`. The commit carrying the task's work is made AFTER that. Mining
therefore runs against a history that does not yet contain the thing it is
mining for.

832's measurement, five samples — episodic file's first-appearing commit vs the
task's earliest commit:

```
T-505  episodic added 2026-08-14T22:35:16   task commit 2026-08-14T22:35:16   IDENTICAL
T-496  episodic added 2026-08-14T10:04:57   task commit 2026-08-14T10:04:57   IDENTICAL
T-473  episodic added 2026-08-12T22:46:15   task commit 2026-08-12T22:46:15   IDENTICAL
T-418, T-403: same, to the second.
```

Identical because they are the SAME COMMIT. The episodic is written, then staged
alongside the work it failed to find, then committed together. Not a race, not
flaky — guaranteed for this workflow.

**The population has the predicted shape, measured here (2736 episodics):**

```
577 false zeros, by commit count:
  1 commit  : 403     <-- 70%
  2 commits : 106
  3 commits :  37
  4+        :  31
```

403 of 577 have exactly one commit; 509 of 577 (88%) have two or fewer. The tasks
that record zero are precisely the ones whose entire history landed in a single
commit at completion. Anything committed DURING the work is mined correctly —
which is why the field looks healthy in aggregate and the bug is invisible at the
population level: the populated majority and the broken minority are the same
field.

**The control, applied to this claim too.** `commits: 1` appears many hundreds of
times across the corpus, so `0` here is not "the mining never runs". It runs,
looks, and correctly reports what git contained at that instant. The value is not
corrupt. It is STALE BY CONSTRUCTION, and it is never revisited.

**Why it is worse for the tidiest work.** T-3129's guard bug is consistently
wrong in worktrees — once known, it is a category. This one is wrong exactly for
single-commit tasks, i.e. the small, clean, well-scoped ones, and right for the
sprawling multi-commit ones. The memory understates its best work, and nothing
about the file says which kind you are reading.

## Two things the fix has to decide (neither obvious from outside)

1. **Where the refresh hangs.** Regenerate-after-commit is the natural repair,
   but the completion gate runs BEFORE the commit by design — that ordering is
   what lets it block. So the refresh has to hang off the commit, not off the
   completion, and `commits:` then becomes a field written by a different agent
   than the rest of the episodic.

2. **The control cannot live in the suite as usually written.** Complete a task,
   commit, then assert `commits > 0` and it passes — because by assertion time
   the commit exists. The control has to capture the value AT GENERATION and
   compare it to the value after the commit lands. Same trap as T-3129's
   worktree case: run it from the wrong vantage and it is green.

## Sequencing

Converges on `agents/context/lib/episodic.sh` with T-3129. Lands AFTER T-3129,
not alongside it. Fan out on reads, fan in serially on writes.

If T-3129's AC3 (a skipped measurement must emit absent/null, never 0) ships
first, part of this task's damage is already representable — but AC3 does not fix
this, because here the mining is not skipped. It runs and returns a truthful zero
about a history that is about to change.

## Recommendation

**Recommendation:** GO — the mechanism is landed, deployed and exercised on live
data. The one open question is genuinely yours: whether a post-commit hook
rewriting four fields of a file the completion path generated is the seam you
want.

**Rationale:** The ordering that causes this is not a bug and must not be
changed — the completion gate runs before the commit precisely so it can block.
That leaves only one lever: re-ask the question from a vantage point where the
answer exists. Post-commit is the earliest such point, and it is already
installed everywhere the framework is.

The cost is real and I would rather name it than have you find it: the four
mined counters are now written by a different agent than the rest of the
episodic. I mitigated that by putting the provenance in the artefact
(`footprint_refreshed_at`, `footprint_refreshed_by_commit`, directly beneath
`lines_removed`) rather than only in `## Decisions`, so a reader sees the split
where the numbers are. But it is still a split, and if you would rather have a
scheduled reconcile, or the field left stale by design and documented as such,
this re-hangs cheaply — the mining logic is one module and the hook call is six
lines.

**Evidence:**

- `lib/episodic_footprint.py` — new; mines with the same `--all --grep="<id>:"`
  shape as `episodic.sh` so the refreshed value is comparable to the generated
  one rather than a second, subtly different measurement.
- Exercised on live data before any claim: T-3133's episodic read
  `commits: 1` against 2 actual commits; the refresh corrected it to
  `commits 1->2, files_changed 9->34, lines_added 1512->2450,
  lines_removed 4->110`.
- Deployed, not merely wired (L-364): `.git/hooks/post-commit` on disk is
  `VERSION=1.7` and contains the call. Verification asserts the **deployed**
  file, not the template.
- Control: 11 tests, fixtures only (L-599) — no live task id, no dependence on
  the 577-episodic backfill population, so it still passes after that runs.
- Mutation-checked twice, because the first number was weak. 11/11 fail against

- T-3129 boundary is enforced, not trusted: `git_mining: skipped` episodics are

**What you are being asked:** read the `## Decisions` entry on AC4 — it names the

## Decisions

**Where the refresh hangs, and why it could not hang anywhere else (AC4).**
The refresh is attached to the **post-commit hook**
(`agents/git/lib/hooks.sh`, template `# VERSION=1.7`), which extracts every
distinct `T-NNNN` from the commit message and calls
`lib/episodic_footprint.py` for each one that already has an episodic.

The completion path was never a candidate. `fw task update --status
work-completed` generates the episodic *before* the commit carrying the work,
and that ordering is load-bearing: the completion gate runs ahead of the commit
precisely so it can block. Moving generation later to get a better number would
trade a reporting defect for a governance one. So the vantage point has to
change, not the ordering — and post-commit is the first moment the commit being
described exists.

**Consequence, stated because it is a real cost.** The four mined counters are
now written by a different agent than the rest of the episodic: the completion
path writes the file, the post-commit hook rewrites four of its fields. That
split is visible in the artefact rather than only here — a refresh stamps
`footprint_refreshed_at:` and `footprint_refreshed_by_commit:` directly beneath
`lines_removed:`, so a reader looking at the numbers sees who last touched them
without going to a Decisions section. Repeated refreshes replace that stamp
rather than accumulating it.

**Alternatives rejected:**

- *A scheduled reconcile* (cron sweeps episodics and re-mines). Correct
  eventually, but it puts an unbounded window between the artefact and the
  truth, and cron drift is a class this repo already tracks in three places
  (L-364's registry→generated→deployed chain). Post-commit has no window.
- *Leaving the field stale by design and documenting it.* This is what was in
  effect, undocumented. The failure mode is that `commits: 0` beside
  `git_mining: ok` is indistinguishable from a task that genuinely produced no
  commits — the same false-zero shape T-3129 fixed one layer up.
- *Regenerating the whole episodic post-commit.* Rejected: it would overwrite
  the narrative sections a human or agent may have edited between completion and
  commit, to fix four numbers.

**Boundary with T-3129, and why it is enforced in code rather than trusted
(AC5).** T-3129 makes an *unmeasurable* footprint `null` with
`git_mining: skipped`. This task's zeros are *measured and truthful at the
instant taken*. Post-commit always runs inside a git repo, so this module
**could** fill in the `skipped` ones — and that is exactly why it refuses to.
Silently flipping `skipped` → `ok` from a different code path would erase the
evidence that generation-time mining failed, which is the signal T-3129 was
built to produce. Those are repaired by backfill, under their own task, where
the population is counted. Two tests pin the distinction, including one that
runs both states through the same repo and the same commit history and asserts
they diverge.

**PL-078 was tripped during this task, on this task.** Bumping the `# VERSION=`
literal inside the commit-msg heredoc did **not** cause a redeploy —
`install-hooks` short-circuits on the separate constant
`COMMIT_MSG_HOOK_VERSION` at `hooks.sh:27`, and it still read `1.14`.
`fw git install-hooks` reported "Hooks already installed" and the post-commit
hook on disk stayed at `VERSION=1.6` with no wiring, while the template said
`1.7`. Caught by reading the deployed file rather than trusting the installer's
success message — the same wrapper-vs-wrapped confusion that has cost this
session three wrong claims. The file's own comment says to bump both; there is a
`tests/unit/hook_version_marker_parity.bats` guarding it. Both constants are now
`1.15`/`1.7` and the deployed hook is verified by grep, not by the installer's
say-so.
