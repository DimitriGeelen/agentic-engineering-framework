# T-3130: episodic mining runs before the completion commit exists, so single-commit tasks record zero by construction

## Context

Second, independent root cause of the same symptom as T-3129 (false `commits: 0`
in episodic memory). Reported by 832-Workflow-designer, who checked our G-041
report against their own tree rather than assuming it did not apply — and found
the symptom reproduces on a NORMAL checkout, where the T-3129 guard passes.

**The ordering.** The episodic is generated by `update-task.sh --status
work-completed`. The commit carrying the task's work is made AFTER that. Mining
therefore runs against a history that does not yet contain the thing it is
mining for.

832's measurement, five samples — episodic file's first-appearing commit vs the
task's earliest commit:

```
T-505  episodic added 2026-08-14T22:35:16   task commit 2026-08-14T22:35:16   IDENTICAL
T-496  episodic added 2026-08-14T10:04:57   task commit 2026-08-14T10:04:57   IDENTICAL
T-473  episodic added 2026-08-12T22:46:15   task commit 2026-08-12T22:46:15   IDENTICAL
T-418, T-403: same, to the second.
```

Identical because they are the SAME COMMIT. The episodic is written, then staged
alongside the work it failed to find, then committed together. Not a race, not
flaky — guaranteed for this workflow.

**The population has the predicted shape, measured here (2736 episodics):**

```
577 false zeros, by commit count:
  1 commit  : 403     <-- 70%
  2 commits : 106
  3 commits :  37
  4+        :  31
```

403 of 577 have exactly one commit; 509 of 577 (88%) have two or fewer. The tasks
that record zero are precisely the ones whose entire history landed in a single
commit at completion. Anything committed DURING the work is mined correctly —
which is why the field looks healthy in aggregate and the bug is invisible at the
population level: the populated majority and the broken minority are the same
field.

**The control, applied to this claim too.** `commits: 1` appears many hundreds of
times across the corpus, so `0` here is not "the mining never runs". It runs,
looks, and correctly reports what git contained at that instant. The value is not
corrupt. It is STALE BY CONSTRUCTION, and it is never revisited.

**Why it is worse for the tidiest work.** T-3129's guard bug is consistently
wrong in worktrees — once known, it is a category. This one is wrong exactly for
single-commit tasks, i.e. the small, clean, well-scoped ones, and right for the
sprawling multi-commit ones. The memory understates its best work, and nothing
about the file says which kind you are reading.

## Two things the fix has to decide (neither obvious from outside)

1. **Where the refresh hangs.** Regenerate-after-commit is the natural repair,
   but the completion gate runs BEFORE the commit by design — that ordering is
   what lets it block. So the refresh has to hang off the commit, not off the
   completion, and `commits:` then becomes a field written by a different agent
   than the rest of the episodic.

2. **The control cannot live in the suite as usually written.** Complete a task,
   commit, then assert `commits > 0` and it passes — because by assertion time
   the commit exists. The control has to capture the value AT GENERATION and
   compare it to the value after the commit lands. Same trap as T-3129's
   worktree case: run it from the wrong vantage and it is green.

## Sequencing

Converges on `agents/context/lib/episodic.sh` with T-3129. Lands AFTER T-3129,
not alongside it. Fan out on reads, fan in serially on writes.

If T-3129's AC3 (a skipped measurement must emit absent/null, never 0) ships
first, part of this task's damage is already representable — but AC3 does not fix
this, because here the mining is not skipped. It runs and returns a truthful zero
about a history that is about to change.

# ── Pipefail/SIGPIPE: grepping a command's output (L-387, T-2090, T-2743, T-2738) ──
#
# THE DEFAULT — redirect to a file, then grep the file:
#     cmd > /tmp/.out 2>&1 && grep -q "PATTERN" /tmp/.out
#     curl -sf "$(bin/fw watchtower url)/page" -o /tmp/.out && grep -q "PAT" /tmp/.out
# Correct at any output size, and `&&` keeps the PRODUCING command's exit code in
# the verdict. Reach for this first; the alternative below is the special case.
#
# Why not `cmd | grep -q PAT` (L-387): P-011 runs each line under `set -eo
# pipefail`. When grep matches it exits and closes stdin while cmd is still
# writing, cmd takes SIGPIPE, the pipeline exits 141 — verification "fails" with
# the pattern present. Captured 4× (T-1716, T-1838, T-1862, T-1863).
#
# THE EXCEPTION — capture first, grep the capture:
#     out=$(cmd 2>&1); echo "$out" | grep -q "PATTERN"
# Valid ONLY while "$out" fits the 65536-byte pipe buffer, and it is on you to
# know that it does. Above that the form inverts and becomes the very failure
# L-387 describes: echo blocks on the full pipe, grep -q exits, echo takes
# SIGPIPE, rc=141 (T-2743 — measured on a 146,366-byte Watchtower page, 3/3 runs,
# deterministic not racy; rendered routes run 50-200KB, so anything that curls a
# page is over the line). It also discards cmd's exit code, so a 404 yields an
# empty capture that grep merely fails to match rather than a failed line.
# If you do use it: single pipe only, no intermediate tail/awk/sed stage between
# capture and grep (T-2090) — the middle stage is what `grep -q` slams its stdin
# on, and grep scans the whole captured string anyway, so the `tail -3` was
# cosmetic. `echo "$out" | grep -q PAT`, nothing between.
#
# TEST RUNNERS need a guard either way (T-2738). `set -e` is suppressed inside the
# `if` condition the gate runs each line in, so in `cmd1; cmd2` only cmd2 is the
# verdict — and the pass marker you grep for survives a partial failure: a suite
# printing "3 failed, 9 passed" satisfies `grep -q "9 passed"`, and generalising
# to `grep -qE "[0-9]+ passed"` matches the same output. Keep the exit code:
#     python3 -m pytest <file> -q > /tmp/.out 2>&1 && grep -q passed /tmp/.out
# or add the guard the exit code used to supply:
#     out=$(python3 -m pytest <file> -q 2>&1); echo "$out" | grep -q passed && ! echo "$out" | grep -q failed
#     out=$(bats <file> 2>&1); echo "$out" | grep -q '^ok 1 ' && ! echo "$out" | grep -q '^not ok'
