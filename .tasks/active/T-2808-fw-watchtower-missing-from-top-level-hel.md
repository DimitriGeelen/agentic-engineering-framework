# T-2808: fw watchtower missing from top-level help; serve advertises hard-coded port 3000

## Context

Operator complaint, twice, from a real onboarding run on `/opt/2345-test-install`:
their agent ran `fw watchtower url`, got `http://localhost:3000` with rc=0, and then
found that `fw watchtower` does not appear in `fw help` at all — so there was no way
to discover the verb or learn it has `port|url|status` subcommands.

Verified 2026-08-05: `bin/fw help | grep -c '^\s*watchtower'` → **0**. The only
related lines are `scan` and `serve [--port N]  Start web UI (default port 3000)`.

Two defects in one surface:

1. `watchtower` is a real dispatch target (`bin/fw:5519` — `port|url|status|start|
   stop|restart`) with no help entry. CLAUDE.md tells agents to resolve the port via
   `bin/fw watchtower port|url` and never hard-code `:3000`; the CLI's own help does
   not mention the command that instruction depends on.
2. The `serve` help line states "default port 3000" as fact. The port is per-project
   and resolved triple-file → `FW_PORT` → 3000. Advertising 3000 in help is the same
   literal the T-2732 close gate refuses in Verification blocks — the CLI teaches the
   anti-pattern the framework gates elsewhere.

# for the captures they were written about, and both invert above the pipe
# buffer. `echo "$out" | grep -q PAT` is NOT SIGPIPE-free — it is SIGPIPE-free

# early match: echo blocks on the full pipe, grep -q exits, echo takes SIGPIPE,
# pipeline exits 141 under pipefail — the exact failure L-387 exists to prevent.
# Measured: a Watchtower page is 146,366 bytes, rc=141 on 3/3 runs, deterministic
