## RCA

**Symptom:** Operator perceives repeated session crashes — sessions "tumble", require `/resume`, and land back at the `claude-fw` main screen where the session is not visible in the list. Fear of destroyed work.

**Root cause (two independent mechanisms, neither is data loss):**

1. **Launch mode — running under the background-job daemon, not TermLink (G-098).** Process ancestry of this session walks to `claude daemon run` (pid 1500448) → `claude bg-pty-host` → `claude bg-spare 73cdfa98` → the session bash. Sessions are claimed from the daemon's host-wide "spare" pool (`~/.claude/daemon.log`: `bg claimed-spare d19f07b4 (spare)` at 2026-09-07T20:26:49Z). A spare was **never registered with TermLink**, so `termlink list` cannot show it — that is precisely why "I don't see the session in there." This is the exact class CLAUDE.md §Session Launch Policy names as G-098, which by construction no in-session gate can detect.

2. **The "crash back to menu" is the DISARMED continuous-run loop stopping cleanly — not a crash.** `.context/working/.continuous-mode.yaml` has `enabled: false` (`disarmed_reason: "T-3164: shipped disarmed"`). The Stop hook `agents/context/stop-driver.sh:136` sees not-armed and emits `decision=stop` (allow the session to end), replaying a *stored* reason from 2026-09-03T18:24:48Z (`terminated[stored@...](T-3263 resolved … clearing stale human-gate latch … T-3268)`). `continuous-run.jsonl` confirms every exit is `reason: continuous-terminated, exit_code: 0` — clean exits. The daemon then logs the ended spare as `bg settled … (killed)` — e.g. `638b12a1 (killed)` at 20:10:49Z matches the continuous-run exit at 20:10:49Z exactly. So a driver keeps **starting** sessions (`event: start reason=armed`, restart_count 0, hours apart) and each ends cleanly because the loop is off; the start/stop churn + the daemon's "killed" wording reads to the operator as crashing.

**Work-loss audit — essentially NONE:**
- Unpushed commits: **0**. `git fetch` then `rev-list --count origin/bleeding-edge...bleeding-edge` = `0 0`; HEAD (2d6d4ee48) is contained in `origin/bleeding-edge`. The transient "ahead 1" was a stale remote-tracking ref, cleared by fetch.
- Uncommitted files (73): all auto-churned state — 35 `docs/generated/` regenerated component docs, 35 `.context/` working-memory/audit files, 2 `.tasks/` (T-3211 + this task). No source-code work stranded.
- Handover coverage: handovers generated every ~30–60 min today (22:12, 19:37, 18:42, 18:07, 16:48…), each with a discard manifest. Budget-critical auto-handover fired correctly at S-2026-0907-1917 (306,418 tokens → handover + stored resume directive). 26 commits landed in the last session per its metrics.

**Why structurally allowed:** G-098 is a standing, documented gap — the daemon launches the session before any framework governance loads, so nothing in-session can see or prevent its own launch mode. The perception of loss is amplified because a bg-daemon spare is invisible to `termlink list`, removing the one affordance the operator uses to confirm a session is alive.

**Prevention (already exists / recommended, not net-new code here):** Launch with `claude-fw --termlink` (or `TL_CLAUDE_ENABLED=1 claude-fw`) so the session registers and is visible/attachable. The disarmed loop is *correct* and must stay disarmed (do NOT re-arm). This is an investigation task — no code fix is warranted; the mechanisms are working as designed and the "loss" does not exist.
