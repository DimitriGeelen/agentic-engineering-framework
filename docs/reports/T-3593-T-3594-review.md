## T-3593 — Tier 0 approvals keyed to the action

### VERDICT: RED

Four defects. The first two break properties the task claims. Two smaller ones follow.

**R1. `--no-verify` is folded silently into a force-push approval, and that approval then gets used twice.**
`--no-verify` is a Tier 0 pattern in its own right (`HOOK BYPASS`, check-tier0.sh). `_classify_push` skips long options it does not know, so `git push -f --no-verify origin main` maps to one action, `FORCE-PUSH ref 'main' to remote 'origin'`. That is all the operator sees. The invariant in the module docstring, "every segment the Tier 0 patterns flag is fully explained", is checked per segment and not per pattern. So a segment that matches two patterns is treated as explained once any action comes out of it.
Reproduced (probe A):
1. The operator approves the command above.
2. The text gate admits it.
3. The push skips pre-push, so nothing is consumed and the record stays `admitted`.
4. A second forced push from a script, `bash s.sh`, then passes pre-push on the same approval and consumes it.

The result is one approval, two forced pushes, and a hook bypass the operator was never shown. The legacy exact-text path did not have this hole. This is a weakening, not a like-for-like change.

**R2. An agent can approve its own action approval, and the record says "human".**
- `python3 lib/tier0_action.py approve-pending 300` has no `CLAUDECODE` check. Under `CLAUDECODE=1` it wrote a live approval, and the blocked push was then admitted (probe P3).
- Neither that command nor `bin/fw tier0 approve --i-am-human` trips the text gate (probe P4: rc=0 for both).
- A record written by hand into `.context/working/tier0-action-approvals.json` is admitted (probe P5).
- In every one of these cases `approve()` stores `approved_by: "human"`, and `_bypass_log` hard-codes `authorized_by: human`. The audit trail cannot tell an operator from an agent.

`CLAUDE.md` does name `--i-am-human`. It does not name the direct module path, and "human-only" together with `authorized_by: human` over-claims. At minimum the claim must be stated honestly. Better, add a real check (see guidance).

**R3. The action shown can differ from the action executed (`cd` with `;`).**
`cd /nonexistent; rm -rf .` is shown as `RECURSIVELY DELETE /nonexistent` (probe P6). In a real shell the `cd` fails and `rm -rf .` runs in the *old* cwd. The classifier assumes every `cd` succeeds, whatever the separator (`split_segments` throws the separator away), and it also treats a `cd` inside a pipeline or subshell as changing the cwd. The operator would be approving a description that is false.

**R4 (amber-level). `hard-reset {repo, branch}` leaves out the target commit.**
One approval for "HARD-RESET branch 'main'" admits `git reset --hard HEAD~40` just as it admits `git reset --hard origin/main` (probe P7). The description only mentions uncommitted changes. That matches the spec, but the operator should see where the branch is going to move to.

## T-3594 — pre-push refuses forced updates and deletions

### VERDICT: AMBER

The core property holds and fails closed. A non-fast-forward branch update or a ref deletion, pushed from a script, typed, or in a multi-ref push, is refused without a matching approval, and one approval is consumed exactly once. Fast-forwards, new branches and new annotated tags pass. The problems are one real gap and documentation that claims more than the code does.

**A1. A tag moved forward by force passes with no approval.**
`git tag -f -a v1 <descendant>` followed by `git push -f origin v1` went through (probe B). `merge-base --is-ancestor` peels the old tag to its commit, so the hook reads a moved tag as a fast-forward. Git itself treats every tag update as forced. Release tags are what consumers install from, so rewriting one is exactly the kind of history rewrite Tier 0 exists for. Fix: under `refs/tags/`, any update where the remote SHA is non-zero is `force-push`.

**A2. "However the push was launched" over-claims.**
The hook, `CLAUDE.md` §Tier 0 and the block message name `--no-verify` as the only limit. Probe D shows `git -c core.hooksPath=/dev/null push -f origin main` from a script succeeding with no approval. Typed, the same command, like `git -C <dir> push -f`, is not matched by the text gate at all: its fast-path regex needs `git\s+push`. That second gap predates T-3594 but interacts with it. Any route that does not run git push's hooks has the same hole: `core.hooksPath`, `git send-pack`, or ref updates through a forge API. The text should say "any path that skips client-side hooks (`--no-verify`, a `core.hooksPath` override, API/plumbing ref updates)", and the text gate should learn `git (-c …|-C …) push`.

**A3. An admitted approval can outlive the push it was admitted for.**
If a typed push is admitted by the text gate but never reaches pre-push (it was a fast-forward after all, the network failed, or R1/A2 applies), the approval stays `admitted` and a later script push can consume it within the TTL. That is the second-use mechanism behind R1. Consider expiring `admitted` records quickly, for example after 60 s, instead of after the full grant TTL.

**A4 (minor).**
- `PROJECT_ROOT` comes from `git rev-parse --show-toplevel`. In a linked worktree that points at the worktree's `.context/working`, not the store that `fw tier0 approve` wrote to in the main checkout. This fails closed, but it gives a confusing refusal.
- `_zero` is 40 characters, so in a SHA-256 repository a new-ref push reads as `force-push` (also fails closed).
- The consumption log says `authorized_by: human`; see R2.

### The 5-second T-1508 window — my judgement

The window is not acceptable as the mechanism. It is tolerable as a documented fallback. The right key is the tool call, not the text and the clock: key the sentinel on the PreToolUse payload's `tool_use_id`. It is identical across duplicate registrations of one call and distinct across calls; confirm that this host's Claude Code sends it. Fall back to hash plus 5 s only when that field is missing. Until then, document it in three places:
- in `CLAUDE.md` §Enforcement Tiers, next to "approves each one once": "for 5 s after use, the identical command text is re-admitted to absorb duplicate hook registration (T-1508); a push is still consumed once at pre-push, a reset or rm is not";
- in the same terms in the `check-tier0.sh` sentinel comment;
- in the t3594 test comment, which already calls it "a known residual", together with a pinned characterisation test for the reset case.
