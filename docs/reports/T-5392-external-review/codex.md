1. **[HIGH] Ring20’s integration is placed in the distributed framework.** `agents/audit/node1-nightly.sh`, `node1_nightly.py`, and `node1-incompatible.txt` would be vendored into every consumer. They implement this operator’s arrangement, not a generic framework capability. Move the ring20 runner and exclusion profile into this project’s unshipped `.context/` or an operator-managed installation. If shared functionality is warranted, ship only a generic, optional, **off-by-default remote-test adapter interface**.

2. **[HIGH] Overridable defaults still embed ring20’s identities and protocol.** The Python runner defaults to hubs `ring20-management` and `node1-pool`, client `999-Agentic-Engineering-Framework`, entries `aef2.bats`/`aef2.pytest`, and environment `aef-unit-2`. It also embeds ring20 channels, the `ring20.pool.stage/1` schema, `/usr/local/bin/pool-client`, `termlink`, job prefixes, task identifiers, and node1-specific report/state paths. These belong in project-local configuration or ring20’s adapter. A generic interface should require explicit provider and identity configuration and expose health, staging, submission, and collection without knowing ring20’s transport.

3. **[HIGH] The bundle builder also exports operator-specific assumptions.** Vendored `lib/test-bundle.sh` defaults to `node1-bundles/aef-unit-suite-*`, a 64 MB pool limit, branch `bleeding-edge`, and a fixed exclusion policy. Its claim that excluded history is unnecessary is contradicted by the recorded `test_search_inclusion_set.py` failure. Keep any generic snapshot-building primitive provider-neutral; put destination, size limit, packaging requirements, and content selection in the local adapter profile. Validate the selected tests against the resulting snapshot.

4. **[MEDIUM] The exclusion list is a local compatibility profile, not framework policy.** The list reflects node1’s tools, permissions, timing, networking, and AEF’s own test filenames. Shipping it under `agents/audit/` makes those limitations a default for unrelated consumers and can silently omit similarly named tests. Move it into project-local configuration, retaining reasons and review criteria. Report the actual configured exclusion file and its digest; `build_report()` currently always names the bundled default even when `--exclude-file` overrides it. The assertion that local execution preserves coverage should be verified through the local report.

5. **[HIGH] Option 3 best fits the immediate trial; none justifies shipping ring20’s wrapper as framework code.** Run the reviewed, pinned wrapper through an operator-managed script outside vendored paths. Option 1 is acceptable only as a narrowly scoped, project-local read allowance needed for review; widening access to the entire handoff folder is unnecessary and does not establish execution trust. Option 2 is acceptable only in an explicitly non-vendored, project-specific location—not `agents/`, `lib/`, or another shipped path. The durable shape is a generic adapter interface with ring20’s implementation outside the framework. `/var/lib/ring20-handoff/999/aef-pool-submit.py` must remain a local deployment detail.

6. **[HIGH] Unconfigured consumers need an explicit disabled state.** The supplied scripts have no opt-in gate: invoking the runner can contact ring20 using the default client identity, wait for hours when tools or feeds are unavailable, and potentially upload the consumer’s repository. Require explicit enablement and complete local configuration before any network activity. Disabled installations should neither schedule work nor fail audits for missing pool tools, credentials, or reports. Validate configured installations promptly and preserve a network-free dry run.

7. **[MEDIUM] The cron entry itself is correctly local, but that boundary must remain intact.** The supplied `.context/` registry is not shipped, so its absolute `/opt/999-Agentic-Engineering-Framework/...` command, ring20 description, schedule, and node1 output expectations are **not themselves consumer leaks**. Keep them local and update the command to the relocated runner. Do not propagate this entry or its report requirements into framework defaults or mandatory audit checks. The excerpt does not establish whether the entry is enabled, and scheduling at 03:33 does not establish that the 03:03 local suite has finished.

8. **[HIGH] Nightly execution of the external wrapper requires an explicit trust arrangement.** The wrapper’s source is absent from the bundle; its described behavior and recorded SHA-256 are insufficient to approve its execution. Review the exact artifact and invoked dependencies, enforce the approved digest at execution, control replacement permissions, and require review for updates. Run with a dedicated least-privilege identity, restricted credentials, a minimal environment, and narrowly scoped filesystem access. Separately approve the repository contents sent to ring20: removing three history directories is not a sensitive-data export policy. Bind returned results to the expected job, target, bundle, and toolchain; safely handle remote artifacts.

9. **[HIGH] The proposed wrapper substitution does not yet preserve the scheduling contract.** The supplied implementation still submits directly through `pool-client`; the task update proposes delegating submission and collection to the wrapper. There is no evidence that the wrapper enforces the 12-open limit or checks fresh health throughout submission. Its documented 200-job window is a different constraint. Even the current implementation checks health before a batch, not before each submission. Define these guarantees in the adapter contract, including health checks before staging and subsequent submissions, bounded retries, and collection of already-running jobs during a hold.

10. **[HIGH] Incomplete runs can currently look successful, and completion evidence is missing.** The Python runner can return zero with `not_sent` or `not_collected` results after submission failures or wall-clock expiry, provided no new test failure was recorded. That contradicts the wrapper’s stated “never zero on could-not-look” rule and risks a green nightly status without coverage. Give incomplete runs an explicit non-success status and expose them in the nightly report. Reset unsupported acceptance checkmarks: the bundle supplies neither the wrapper integration nor evidence of the required successful ≤20-file trial. Verify the selected final execution path before enabling nightly operation.
