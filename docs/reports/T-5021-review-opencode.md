# Independent review — T-5021 requirements collector output (T-3580)

**Findings, most severe first:**

1. **R-29 over-claims what the gate can enforce (§6.6.4 vs C-7/§7.7, 10.8).** R-29 (P1) says public text on *both* routes MUST pass the gate and it MUST be impossible for listed classes to appear — yet C-7 itself records that a trusted peer holding a token can post with any GitHub client, bypassing it. The same hole applies to AEF's own token: a confused agent (2.7.c, which R-29.d claims to hold against) can call the API directly; the gate lives inside the adversary. The acceptance criterion "submitted on either route, then the gate refuses" is untestable on the direct route. Fix: scope the impossibility to the relay route; add a *decided* direct-route control (e.g. `fw issues sync` must scan every post, hide hits, flag and alert the operator; or narrow direct posts to templated verdict comments), and apply it to AEF's token too.

2. **Nothing restrains 2.7.d at the merge (§2.7, R-4/R-21/R-24).** R-21.d and R-6.d name the hurried approver, but no requirement makes merging without green checks or the recommendation *impossible* — enforcement rests entirely on the operator's discipline, and red CI already ran unnoticed three times (4.6.b, 10.13). Fix: new requirement — branch protection on `bleeding-edge` MUST require passing R-12 status checks (and, if feasible, a review) before the merge button works.

3. **Token scope feasibility unverified (R-37/R-38, §6.7).** GitHub fine-grained PATs have no "issues and PR comments only" permission: comments ride on Pull-requests: write, which for a write-role account may permit merging PRs. R-37.c's "cannot push or merge" may be unimplementable as scoped. Fix: verify against GitHub's permission model; if the granularity does not exist, enforce operator-only merge via required-review branch protection (synergises with finding 2).

4. **Field tests run a stranger's code on estate hosts before any isolation floor exists (R-18, C-2/10.9, R-15).** R-18 (P1) is enforced only "by the procedure AEF sends"; throwaway-copy isolation (10.9) is open and the own runner is P2 (R-15), while the pilot (R-7, P1) can merge before either lands. Fix: gate the pilot's first field test on a P1 isolation floor (10.9 decided or own runner live), or cap pilot PRs at risk levels needing no field test until then.

5. **PR-modified workflows not covered (R-12/R-13/R-14, §6.3).** `pull_request` runs the workflow file from the PR branch; R-14 ("framework commands only") does not forbid `pull_request_target`, repo secrets, or over-broad `permissions:` in PR-triggered workflows. Fork PRs get no secrets by default, but that default is exactly what a requirement should pin against 2.7.a. Fix: require PR-triggered workflows to use no repo secrets and a minimal token, and PRs touching `.github/workflows/**` to get explicit operator approval before any run.

6. **Completion-condition defects (card 6.1–6.3).** (a) 6.11 counts 18 "impossible" requirements with item d; I count 17, and R-13 (a MUST NOT security invariant) has no item d at all. (b) R-26 adds "and replies" to what stays on the sidecar — no A-n/F-n supports it (violates 6.0.d). (c) A15's "advisory published with the fix" is not carried into R-35. (d) 4.2.a "A7 to A9: not yet asked" is stale, contradicting 4.7–4.9. (e) 4.18.e's recovery claim leans on a local issue ledger that no requirement requires. Fix: add R-13.d, correct 6.11, source or drop "replies", carry the advisory clause, delete stale lines, add a ledger requirement or drop the claim.

7. **Weak acceptance criteria (card 6.2).** R-7.c ("not recommended for merge") is passed by an implementation that never recommends anything; R-15.c's first clause ("task exists with high priority") is passed by creating a task entry; R-39.c's "refused or flagged" leaves the flagged-but-applied case open. Fix: R-7 — no review, test or merge occurs and the PR is answered per 10.2; R-15 — keep the same-verdict criterion as the only testable one; R-39 — "the write does not take effect until the operator records approval".

8. **10.7 (spoofable project-id stamp) has an available fix not recorded (R-34, §6.6.9).** Each trusted peer holds its own token, so identity can be derived from which token created the post (registry: token→peer), with any mismatch between token-mapped id and stamped id refused or flagged. Fix: record this as the recommended option under 10.7 so R-34's stamp is trustworthy; leaving it fully open weakens R-34 to decoration.

9. **Minor: D-2 pre-decides open C-6** by listing "DCO" among the GitHub checks while 10.6 leaves where the DCO check runs open. Align the drawing or mark that node provisional.

Coverage and fidelity otherwise check out: every A-n and F-n I could trace maps to a requirement or a recorded open question; earlier requirements (Mehdi's eight points) are correctly kept/changed/dropped with reasons; no conflict is resolved by the author where only the human may decide (recommendations are labelled as such); drawings D-1..D-3 have ids, captions and textual equivalents consistent with the requirements.

**Verdict: amber** — faithful and well-traced overall, but R-29's unenforceable impossibility claim, the missing merge-block against the hurried approver, the unverified token-scope granularity, and the completion-condition nits (finding 6) need fixing before the operator's sign-off.
