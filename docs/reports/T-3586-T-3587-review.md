## A. T-3586: does batch-complete on /approvals still complete a ready task?

### VERDICT

**AMBER.** T-3586's change is correct and narrowly scoped, and it works. It completed a real task through the real handler under CLAUDECODE=1, while the same command run directly was refused. However, I did **not** click the live button, and the operator should not click it either. The live /approvals page shows **"Complete 2 Ready Tasks"** for T-2200 and T-2202. Both are `started-work`, both are `owner: human`, and each has an **unchecked `[REVIEW]` Human criterion**. One click would close both, with `--skip-sovereignty --skip-verification --skip-acceptance-criteria`. The defect is older than T-3586, but T-3586 is what keeps the path usable, so it needs fixing before this gets a green.

### WHAT I CHECKED

1. **The strip is legitimate and scoped.** `complete_batch()` (approvals.py:975-985) removes only `CLAUDECODE`, and only for the `fw task update` subprocess inside that route. The rest of the environment is inherited. It is the same pattern as T-1193's inception-decide path (approvals.py:918-925), which also adds `TIER0_AUTOEXEC`. The batch path does not add it and does not need it. No other route strips the variable. The reason string, "Batch completed via Watchtower UI (human action)", satisfies T-3586's reason requirement, and each consumed flag is logged. The logic matches `--from-watchtower`: a Watchtower click is the operator's own act.
2. **Negative control: direct CLI refused.** I created throwaway T-3590 (build, owner human) with an unchecked Agent criterion, a checked Human criterion, a `false` Verification line, and status started-work. Running `CLAUDECODE=1 bin/fw task update T-3590 --status work-completed --skip-sovereignty --skip-verification --skip-acceptance-criteria --reason …` returned `ERROR: --skip-sovereignty is refused in an agent session (CLAUDECODE=1) — T-3586`, and the task stayed in active/.
3. **Positive: the real handler completes it.** In a `CLAUDECODE=1` Python process, I called the real `approvals.complete_batch()` view in a Flask request context. I stubbed `_load_pending_human_acs` to return only T-3590, so no real task could be touched. The result was `Completed 1 task(s): T-3590`, and the file moved to `.tasks/completed/`. The bypass log shows `--skip-sovereignty`, `--skip-acceptance-criteria` and `--skip-verification`, each carrying the Watchtower reason. The subprocess, the gates and the env strip were all real; only the list of ready tasks was substituted.
4. **Why I did not POST to the live endpoint.** `complete_batch` completes *every* ready task and takes no task id. I computed its ready list locally with the live code and got `['T-2200', 'T-2202']`. The live page confirms this (`hx-confirm="Complete 2 task(s) with all Human ACs checked?"`). A live POST would have closed two real open tasks.
5. **Root cause of the false readiness.** `_load_pending_human_acs` admits a task using `needs_human_review` (`count_unchecked_human_acs`). T-3139 made that count every `### Human` block, including one after an intervening `## Status:` heading. The ready test at approvals.py:955 uses `_parse_acceptance_criteria` (tasks.py) instead, and that still stops at the `##` heading. In T-2200 and T-2202 the `### Human` block sits under `## Status: COMPLETED 2026-06-09`, so the parser sees zero Human criteria, and "all checked" is vacuously true. `complete_batch` also never checks status, so the T-1568 comment ("Batch operates on partial-complete tasks (already work-completed in active/)") does not match the code. Here it would close two `started-work` tasks.
6. **Residual, not a blocker.** Any local agent can obtain a CSRF token with curl and POST this endpoint. T-1193's decide path has the same posture. The bypass log records "human action" and nothing distinguishes an agent-originated POST. That is worth naming in T-3586's "does not claim" text rather than fixing here.

**Cleanup:** T-3590 was never committed. I deleted `.tasks/completed/T-3590-throwaway-batch-complete-check.md` and `.context/episodic/T-3590.yaml`. The following entries remain in append-only logs, which I did not edit because they are audit trails:

- `.context/working/feedback-stream.yaml`: two T-3590 rows.

3. **(Note)** Add the agent-can-POST residual to T-3586's "what this does not claim". Once item 1 lands, a quick live re-check with a throwaway partial-complete task, when no other task is ready, would take this to green.
