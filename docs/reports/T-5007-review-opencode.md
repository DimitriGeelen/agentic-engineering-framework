# T-5007 review — findings, most severe first

**1. Relay-filed issues are "internal" to `fw issues sync`, so the whole promised lifecycle silently doesn't apply to them.** In `lib/issues.py`, `_classify`/`cmd_sync` mark any issue authored by the repo owner as internal (lines 724, 733–744): "ledger only, nothing posted" — no Received/Classified comment, no labels, and `cmd_close` (T-4088) closes internal issues on one comment with no submitter confirmation. Option 1 has AEF file under the operator's `gh` login, so every relayed peer request lands in the one path that has none of the public thread/stages/confirmation the move was meant to gain. Fix: relay must post from a dedicated AEF bot account (making it a prerequisite, not an optional extra), or sync needs a "filed-on-behalf-of" marker that forces external treatment regardless of author.

**2. The only existing scrubber cannot do the job the design assigns it, and it currently runs only on release evidence, never on issue bodies.** `_scrub` (lib/issues.py:1435–1448) catches local-suffix hostnames, IPv4/IPv6 and *this machine's* hostname — its own docstring concedes "names the scrub cannot recognise are not caught". It misses absolute paths (`/srv/project-x/...`), account names (`dimitri@`, `ssh deploy@`), tokens (`ghp_...`), and dotted public-style hostnames (`build01.example.net`). Example: a peer bug report "agent on build01.example.net crashes in /home/dimitri/tree/lib/foo.sh for user dg" passes `_scrub` unchanged — and today `_scrub` is applied only inside `_evidence_block`, not to a relayed issue body or title at all. The mirror is public and instantaneous; a leak is never undone. Fix: the shared cleaning function must be path/username/secret-scanner based (gitleaks-class), run on title and body, default-deny (redact anything unrecognized rather than pass-through), with a `--dry-run` review gate for the first posts per project.

**3. Naming the source project in the issue is itself a disclosure, and body-only provenance is untrusted.** "AEF files it with the source included" publishes your private fleet's project names — `acme-erp-bot` may reveal more than any hostname. And since anyone can write "from project X" in a body, `fw issues sync` cannot trust it. Fix: a registry of public aliases per peer project; provenance carried by authorship (bot account) or a repo-side allowlist, never free text.

**4. The loop-back does not reuse the existing lifecycle; a FAILS verdict has no reopen, and the 14-day sweep can close the issue before the sidecar verdict arrives.** `cmd_release` merely *holds* on FAILS ("file a new task", lib/issues.py:1666); there is no reopen verb anywhere. `_sweep`/`_close_issue` count only GitHub replies after the Released comment (`_replies_since`) — a sidecar field report is invisible to it, so the issue closes "no reply in 14 days" while the peer's verdict is still in flight. And `confirm_close` requires the reply to be by the *issue author*: for a relay-filed issue that's the operator, so the peer's confirmation can never close it through the normal path (compounding finding 1). Fix: peer verdict must be posted on the issue (by the peer bot or the relay) and counted; add a reopen stage; suppress the sweep while a sidecar verdict is pending.

**5. Bot accounts: unowned in the design.** GitHub's terms permit machine accounts only as registered by an individual human who accepts the ToS on their behalf — all bots would be the operator's, one liability. Tokens live one per host with no registry mapping bot↔project, so revocation after one host compromise is guesswork; a stolen token posts publicly as a "trusted" peer. And sync's only peer-identification is the hard-coded `ROUTES` dict (lib/issues.py:535) — a peer bot is indistinguishable from Mehdi. Fix: declarative bot registry (like `policy/review-backends.yaml`), fine-grained PATs scoped to issues-write on this one repo, `source:` label family (LABELS currently rejects unknown names) applied at intake.

**6. The relay is a single point of failure and the operator is the bottleneck.** Every peer's fallback is "report to AEF": AEF's host down or its agent busy stalls all intake. Every relayed issue's decision stages (accepted/duplicate/not-planned) need an operator approval unless the standing-permission key is on (cmd_comment:456) — N projects of volume through one decider. Disagreement/rejection feedback to peers is unspecified (pickups had reject/defer replies; `not-planned` on GitHub says nothing back on the sidecar). And the loop-back still needs the sidecar, so the sidecar is a dependency anyway — two channels that must both be alive. Fix: rejection reply over sidecar as part of the flow; batch/standing approval for peer-bot-filed issues; document that AEF downtime degrades to today's pickup path.

**7. Duplicates get weaker, not stronger.** Pickup dedup (content hash + project/task/type triple, lib/pickup.sh) is abandoned on the GitHub route; sync's dedup is a 0.6 Jaccard title hint "never a decision". One bug from two projects plus an outside contributor yields three issues with no verdict cross-propagation — confirming one closes nothing else. Fix: carry the triple key into the issue (e.g. in the relay's provenance block) and link duplicates so a released/confirmed verdict settles all of them.

**8. Migration mechanics are missing entirely.** No plan for the 82 processed pickups (back-file or archive-label?); `fw pickup send --type bug-report|feature-proposal` still delivers over the sidecar and must be wrapped or retired (and `learning`/`pattern` types are unallocated by the operator's "structural" ruling); the human-facing issue templates (`.github/ISSUE_TEMPLATE/bug-report.yml`) have no source-project/agent fields; test.yml ignores everything but main/master (T-5006).

**Verdict: unsound as specified** — the relay route defeats its own purpose (internal classification, no lifecycle, no peer confirmation), the cleaning step as it exists cannot stop the leaks it exists for, and the FAILS loop-back has no reopen path; fixable, but only after findings 1–4 are designed in.
