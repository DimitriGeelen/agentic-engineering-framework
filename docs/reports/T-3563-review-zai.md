## Review — T-3563: what an arc should carry

**1. What an arc should carry.** The arc should be a *routing document*, not a narrative container: current truth in bounded hand-written fields at the top, append-only registries below, everything long behind links. Concretely:

- `purpose` — ≤25 words, hand-written, mandatory: what this arc is and why it exists.
- `context` — 3–6 bullets, written once at creation: problem, who it's for, why now; bullets may link into the anchor inception.
- `non_goals` — explicit scope boundary; cheap to write, prevents creep, orients cold readers.
- `objective` — ≤40 words: the outcome state when done. This is the sentence L3 judges.
- `supports` — IDs of the project objectives this arc serves (upward trace).
- `headline_mechanic` — unchanged.
- `evidence` — named-link map: inception report, dialogue log, design docs, demo artefact.
- `decisions` — append-only registry: `{id, date, ≤20-word summary, status: active|superseded|reversed, source link}`.
- `history` — one line per arc-level event (created, pivot, scope cut, driver change, closed).

**Not on the arc:** task lists and status (derivable from members), verbatim dialogue or full dispositions (they live in the inception), any prose over ~50 words (goes to a linked `.md`), anything a hook can compute. The governing rule is *index, don't copy* — the inception stays the single source of depth.

**2. Headline versus story.** Keep them separate. The headline is a test oracle: it powers L4 and exists precisely because arcs used to close on "substrate in place." Fold it into narrative and it becomes unfalsifiable prose — you'd break the one thing that currently works. The loss from keeping it separate is two purpose-statements potentially diverging; mitigate with a fixed hierarchy: `objective` says why, `headline_mechanic` says how that is demonstrated. One sentence each, different jobs, no overlap in wording.

**3. Derived or written.** Both, with a strict split. **Derived** (regenerated by hook on arc-affecting events, marked `derived: true`, never hand-editable): evidence links, decision-registry entries (title + link extracted from inception dispositions), membership counts. **Written**: purpose, context, non_goals, objective. Anti-staleness: written fields carry `reviewed_on`; hooks set `stale_since` on any pivot, scope cut, driver change, or anchor closure, and both pivot handling and closure require re-confirmation — a gate, not goodwill. Anti-drift: hand-written fields are word-bounded (small drift surface) and must link to their evidence; long-form lives only at the link targets, so there is one source of truth plus a small, checkable summary.

**4. Goals and drivers.** One written `objective` per arc. Extend the existing automated driver-admission reviewer to require each scoped driver's rationale to cite the objective. Reword L3 from "goals achieved" to "the anchor recommendation explicitly disposes the arc *objective*." Trace upward via `supports: [project objective IDs]`, verified the same way demo evidence already is (existence + traceability). Then project objective → arc objective → drivers → task BVP all reference the same written sentence, and closure judges against it.

**5. Evolution.** Two zones. Current truth (purpose, objective, active drivers, non_goals) is edited in place and always reflects now. History lives only in the append-only registries: a reversal is a *new* decision entry that supersedes the old one (`status: reversed`, `superseded_by:`) — history preserved, latest-wins for reading. Scope cuts add a decision entry and a non_goal. Cap `history` at ~20 lines; roll older entries into an archive file linked from the arc. A reader reads top-down and stops when satisfied.

**6. For agents.** Fixed schema over free prose; word-bounded fields so the whole arc parses in ~1–2 KB; stable IDs on every link so an agent can fetch inception depth on demand (progressive disclosure — the arc is the index, the inception is the depth). Mark each field derived vs written with `reviewed_on` so an agent knows what to trust. Front-load status, purpose, objective, headline; put registries last so truncation costs least. Graceful degradation: if prose is thin, the links still carry the load — which is why pointers must be mandatory where prose cannot be.

**7. What makes this fail.** The named failure mode: mandatory fields filled with boilerplate. Mitigations: (a) very few mandatory prose fields (purpose, objective only); (b) word bounds enforced by lint; (c) extend the driver-admission auto-reviewer to reject template phrasing — a purpose containing no arc-specific noun fails; (d) pointer-over-prose as the fallback, so the cheap compliant path is a good link, not filler sentences. Secondary risks: double-maintenance divergence (kept small by index-don't-copy), the decision registry becoming a dump (require a source link; cap entries), and new gates jamming closure (reuse the existing L-legs; only sharpen L3's wording).
