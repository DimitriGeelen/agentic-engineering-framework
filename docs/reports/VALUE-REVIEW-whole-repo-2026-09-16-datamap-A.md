## Notes for the orchestrator

**1. The three ABSENT rows that matter most are 3, 4 and 12 (complexity, duplication, coverage).**
Together they remove the entire *intrinsic code-quality* axis. Nothing on this host can say how
complex a file is, whether it duplicates another, or whether a test touches it. Any value judgment
about a file will therefore rest on **git-derived signal (rows 6, 8, 10) plus the fabric index
(rows 1, 5)** — both of which are about *change history and declared structure*, not code quality.
State that limitation explicitly in the review rather than papering over it.

**2. "No data is not zero" — three live traps I found, flagged so nobody trips them:**
- `.context/monitors/liveness.jsonl` is 2.1 MB and last written **2026-08-14**. The file's presence
  reads as "we have liveness data"; it is five weeks stale. Silence ≠ health.
- `.context/audits/unit-suite/LATEST.yaml` reports the pytest leg as `tests: 0, failed_count: 0,
  exit: 124`. Zero failures because **zero tests ran** (timeout). A naive read says "pytest is green".
- `.context/working/.tool-counter` / `.budget-gate-counter` are **reset to 0 by `fw context init`**
  (`agents/context/lib/init.sh:70,73`). They measure the current session, not the project.

**3. The single most consequential absence for a *value* review: there is no per-`fw`-verb usage
counter.** `.hook-counter` records hook fires and `dispatches.jsonl` records dispatches, but nothing
records which of the ~100+ documented `fw` subcommands are ever invoked. The question "is this verb
used?" is **structurally unanswerable from stored data** — it would need prospective instrumentation
in `bin/fw`. Do not let anyone infer non-use from the silence. (This is also precisely why the
read-only / no-fw-verbs constraint on this review matters: running verbs would have written the only
counters that do exist.)

**4. Churn needs scoping before use.** The top three churn areas are `.context` (27,781),
`.tasks` (20,925) and `.agentic-framework` (6,659) — governance state and a vendored self-copy, not
source. Source dirs are 1-2 orders of magnitude below. Unscoped churn will rank bookkeeping as the
hottest code in the repo. Same correction applies to change coupling (row 8): ~80% of commits are
multi-file largely *because* a task close writes task + memory + fabric together.

**5. The fabric is the only structural index, and it is measurably incomplete.** 1,268 cards, but
**`depended_by` populated on only 461 (36%)** and **`purpose` still `TODO` on 746 (59%)**. Reverse-
dependency questions ("who calls this?") — which are exactly the questions a value review asks — are
the *worst*-covered half of the graph. Treat a missing `depended_by` as unknown, never as "nothing
depends on this."

**6. CI is not where it looks like it is.** `.github/workflows/test.yml` fires only on `main`/`master`;
development lives on `bleeding-edge`, which `master` only receives at release. The real continuous
signal is the local nightly cron suite, whose entire 8-day recorded history is non-zero exit
(`runner_exit=1` on every line of `runs.log`). Whatever CI history exists on GitHub/OneDev is
**UNVERIFIED** from here — neither was reachable/fetchable for this review.

**7. Author concentration has no variance.** >98% of 9,221 commits are one human identity (across
four email spellings — including a typo'd address that is the *dominant* one). Ownership/bus-factor
analysis is not informative here. The separable sub-population is machine authors
(`*@aef.local` dispatch workers, `Agent <agent@local>`, `Claude Code <claude@local>`), which is a
usable signal for "what did dispatched workers produce" if anyone wants it.

**8. Commit subjects are prose, not structured.** 0/500 conventional-commit prefixes; 50/50 carry
`T-XXXX`. So **route every "why" question through the task file**, not the git subject. Traceability
(row 10) is genuinely the strongest generic source available in this repo — it is the join that makes
the weak rows usable.
