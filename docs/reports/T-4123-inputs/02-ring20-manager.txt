# T-2352 — ring20's input to AEF T-4123: what the estate knowledge platform is for and must do

Answer to AEF's requirements collection (conversation `estate-knowledge-requirements`, 2026-10-12). ring20 is both a
stakeholder (an agent that would read and write) and the platform operator (it runs the estate Qdrant on CT 304,
T-2346). Answers are from ring20's own use; file and task references are in ring20's repository.

What ring20 holds today, for scale: 454 learnings (`.context/project/learnings.yaml`), 614 decisions, 230 concerns
and gaps, 18 failure patterns, 1 994 episodic task summaries, 457 fabric component cards, and ~2 350 task files.

## A Content

A.1 **Should go in, in this order of value:**
1. **Learnings and failure patterns with their fix** (`learnings.yaml`, `patterns.yaml`, healing resolutions).
   These are what I re-discover most often (see C).
2. **Episodic summaries of completed tasks**: one paragraph of what was done, what failed and why. That is the
   unit another project can reuse.
3. **Decisions with their rationale and the rejected options** (`decisions.yaml`, task `## Decisions`).
4. **Fabric component cards** (purpose, interfaces, depends_on), for D.
5. **Design and report documents** (`docs/reports`, `docs/designs`), chunked, as references with a short summary.
   Full text only for curated framework knowledge (the operator confirmed "full text OK for curated framework
   knowledge" on 2026-10-12, T-2325 §8).

A.2 **Must never go in:**
- secret values, tokens, keys, passwords;
- `.env` contents;
- process command lines;
- email or any of Penelope's mail data;
- personal data of people;
- raw command output;
- browser cookies or profile files.

ring20 has standing rules for all of these (never print secret values; nothing about credentials in a shared
store). **One lesson:** redacting by key name fails on encoded copies (a base64 or URL-encoded value slips through).
So the filter must work on value patterns, and be applied when the data is written, not when it is read.

A.3 **Freshness:**
- learnings and patterns: within a day of being recorded;
- episodic summaries: when the task closes;
- fabric cards: within a day of a change;
- reports: when committed.

Weekly is too slow: the reason to ask the estate is a problem I am having *now* that someone solved *last week*.

## B Curation

B.1 **Prune** (stale, wrong or superseded items) helps most. Today a learning that turned out wrong stays and keeps
being recalled. ring20 added `learning-cite.py outcome --result corrected` (T-1724) because of this: a misleading
learning is worse than none.
- **Who decides:** automatic when the source item is deleted or marked superseded in its project; a reviewer agent
  for "looks contradicted by a newer item"; never silently.

B.2 **Collapse** (one item for N projects, all sources kept) helps with search noise. The same Qdrant, Ollama and
Traefik gotchas exist in several projects.
- **Who decides:** a reviewer agent proposes it; it is applied automatically when the items' texts match closely.
  The sources must stay visible.

B.3 **Combine** (synthesise a higher-order practice) is the most valuable but also the riskiest: a synthesis can
state something no source said.
- **Who decides:** a reviewer agent drafts it; the operator approves before it is shown as a practice. Until then
  it is labelled "proposed".

B.4 **What goes wrong without curation:** duplicates crowd the top results, and retired data can be revived by
mistake. Example: the KMS collections on CT 301 were retired on purpose on 2026-10-10 (dimitri-mint-dev T-096) and
must never be restored without a new decision. A store needs a "retired on purpose" marker, not just "absent".

## C Retrieval

C.1 **When ring20 would query the estate rather than its own index:**
- before building anything that another project might already have;
- when an error string is new to ring20;
- when a peer's component is involved.

ring20's own rule (`policy/agent-rules.md`, T-1540) is to search the open queue for the exact symptom string
before diagnosing. The estate store would be the same move, across projects.

C.2 **Real questions from this month:**
1. "Qdrant panics with *Too many open files* after a restore — who has hit this and what limit did they set?"
   (T-2324 restore drill, 2026-10-12; fixed with `--ulimit nofile=65536` / `LimitNOFILE=65536`.)
2. "Has any project already rendered Mermaid diagrams server-side for Watchtower pages?" (T-2349, 2026-10-12:
   ring20 built a pre-render cache; AEF's Watchtower may want it upstream.)
3. "Which project has a OneDev skill action to add an SSH key to a user?" (T-2347: none existed; SMA built it as
   150 T-475.)

C.3 **An answer must carry, to be trusted:**
- source project;
- source path or task id;
- date recorded and date last confirmed;
- evidence type (tested / observed / reasoned);
- superseded or retired flag;
- the score.

Without the source and date ring20 cannot check it, and an uncheckable answer is not used.

C.4 **Ranking:**
- ring20's own items first when the scores are close (they fit its environment);
- cross-project items above its own when they are newer and marked tested;
- superseded items never in the top results.

## D Fabric as a solution finder

D.1 **Yes, I would use it.** The concrete example is T-2349 today. "I am working with Watchtower templates and
Mermaid; which project already renders diagrams before the page loads?" — had the answer been "AEF has a server-side
renderer", ring20 would have reused it instead of building one.

D.2 **A card would need to carry:**
- its purpose in one sentence;
- the technologies it touches (as tags: "mermaid", "qdrant", "flask blueprint");
- the problem it solves, phrased as the symptom someone would search for;
- its interfaces;
- its status (live / experimental / retired);
- the owning project and a contact (sidecar name).

ring20's cards have purpose and interfaces, but not "problem solved" or technology tags in a searchable form. 110 of
398 cards have no edges (`fw audit`, 2026-10-12), so dependency data alone will not find solutions.

## E Model and embedding

E.1 **The proposal is right:**
- a default model, configurable;
- every vector tagged with model and digest;
- one collection per model;
- writes with the wrong model refused.

E.2 **Client-side embedding, with the model fixed per collection.** Reasons from ring20's side:
- **Ollama on .107 is a single point of failure.** It has wedged before (memory: G-176). It is also open on the
  LAN (arc-001 F-3).
- **Server-side embedding would put every project's writes behind that one Ollama.** With client-side embedding a
  project can embed with any Ollama that has the same model and digest.
- **The store only checks the tag**, so the vectors stay compatible.
- **Load:** batches of at most ~64 texts, a retry with backoff, and no embedding at query time on the platform host.

## G Error resolution

G.1 **How ring20 records errors and fixes today:**
- failure patterns and resolutions via `fw healing` (18 patterns);
- gaps and concerns in `concerns.yaml` (230);
- learnings (454) with `learning-cite.py` outcome attribution;
- the task's RCA section (required for bug tasks).

The host's `errors_*` skill service is barely used by ring20.

G.2 **One error class from this month that others probably hit:** `grep -q` in a pipeline under `set -o pipefail`.
grep exits at the first match, the writer gets SIGPIPE, and the pipeline fails although the match succeeded.
- ring20 has a learning for it, yet hit it again today in a verification line (T-2349: `curl … | grep -q` → exit 23).
- Every AEF project's verification gate runs shell lines, so others have almost certainly hit it.

G.3 **Would "N projects hit this, no fix yet" change my work? Yes.**
- It would raise the item's priority and make a tooling fix worth more than a per-project workaround.
- Error Escalation Ladder level C ("improve tooling") becomes clearly justified.

G.4 **Never in an error item:**
- raw output;
- secret values (by value pattern, not key name);
- process command lines;
- `.env` content;
- personal or email data;
- full file contents.

Hostnames and IPs only while the store stays inside the estate; nothing ring20 produces leaves the estate. Store the
error class, a short normalised message (variables replaced), the affected component, counts, last seen, and the
resolution.

## Platform operator constraints (CT 304, ring20)

P.1 **Access:**
- JWT RBAC (HS256 over the master key);
- one read-write token per project per collection set (`qdrant-estate-keys.py token --name NAME --collections …`);
- one estate-wide read-only token;
- the master key is never handed to a project;
- tokens live in Infisical and are never printed.

P.2 **Every collection is registered in `_manifest` before its first write:**
- owner project, model and digest, vector size, data class, retention;
- the probe expects the manifest list (`check-qdrant-estate.py EXPECTED`);
- an unregistered collection is a finding.

P.3 **Quotas:** Qdrant has none built in. Each collection declares a size budget (points and bytes) in `_manifest`,
and the probe alerts above it. CT 304 has 4 cores, 8 GiB RAM and a 64 GiB disk; that is fine for millions of
768-dim vectors, but not for unbounded full-text payloads.

P.4 **Backups:**
- nightly per-collection snapshots, 01:30 Berlin, 7 kept;
- a monthly snapshot-restore test;
- the CT itself in PBS nightly.

Full-storage snapshots are not available in cluster mode, so every collection must be snapshot-able on its own.

P.5 **Load and dependencies:**
- writes in batches;
- no bulk re-embedding against Ollama on .107 during the day;
- the platform never calls Ollama itself (E.2).

P.6 **Data classes:** framework knowledge only. No email ever (Penelope's mail lives in its own store, 050). A
collection's data class is decided by the operator, not by the writing project.

P.7 **Retirement:** a collection or item retired on purpose is marked in `_manifest` and never restored without a
new decision (B.4).

## Missed requirements and conflicts

M.1 **Missed:**
- **"retired on purpose" as a first-class state (B.4).** Without it, cleanup and restore fight each other.
- **Provenance must survive collapse and combine.** The sources are kept and remain clickable, through to the
  project's own file.
- **Write-time redaction by value pattern (A.2), not read-time filtering.**
- **A per-project kill switch:** the operator can stop one project's writes without touching others.

M.2 **Conflicts:**
- **Freshness (A.3) vs curation by a reviewer and the operator (B.2, B.3).** Raw items must flow fast; only
  curated syntheses wait for review. They should be two layers, labelled.
- **Ranking own-first (C.4) vs collapse (B.2).** A collapsed item has many owners; rank it by its sources, including
  ring20's own.
- **Client-side embedding (E.2) vs "writes with the wrong model refused" (E.1).** The store can only check the tag
  the client claims. Enforce it with a spot-check: the platform re-embeds a sample with the declared model and
  compares.
