# RCA: v1.8.0 reached consumers before the release finished (T-3785)

2026-10-04 · operator question: "Where does that come from? It could mess things up, or at least cause a lot of confusion."

## Symptom

The operator's agents were installing "1.8.0" while the agent still reported the release as unfinished. The release took three attempts:

| Attempt | Outcome |
|---|---|
| 1 | Refused at push, rolled back |
| 2 | Refused before tagging |
| 3 | Succeeded |

Final state:
- `master` = `dcf619ab3`;
- tag `v1.8.0` (object `4579b4a5`) points at `dcf619ab3`;
- GitHub Release created.

## Timeline

1. **Attempt 1** (`fw release tag-and-release --bump minor`):
   1. The preflight graded `master` as "clean" (fast-forward available). It compared HEAD with the **local** `master` ref only.
   2. The release committed `1fa02d534` "v1.8.0: reconcile VERSION to 1.8.0" onto `bleeding-edge`, tagged it, and fast-forwarded the local `master`.
   3. Pushing `master` was rejected as non-fast-forward. `origin/master` held `eb49ff9`, a commit ring20-manager had made directly at 07:25Z (see T-3818).
   4. The rollback restored the local `master` and deleted the tag. **It did not undo `1fa02d534`.**
2. The agent merged `origin/master` into `bleeding-edge` as `dcf619ab3`.
3. **Attempt 2** pushed `bleeding-edge` in the same command, then released:
   1. The push published `1fa02d534`, and with it **VERSION=1.8.0 reached origin/bleeding-edge** with no release.
   2. The pre-push hook re-stamped the working-tree VERSION to `1.7.<commits>`.
   3. The release saw a `1.7.x` file, wrote `1.8.0`, and tried to commit. That matched the already-committed content, so the commit was empty: "VERSION reconciliation commit failed". The release refused, correctly.
4. **Attempt 3:**
   1. Fast-forwarded `master` to `dcf619ab3` and pushed it.
   2. Then pushed the tag through a second full pre-push audit (minutes).
   3. **During that window, consumers ran `fw upgrade` from master and installed "1.8.0".** The upgrade reads VERSION from master, not the tag.
   4. The tag landed and the GitHub Release was created.

## Root causes (one bug, one task)

| # | Cause | Code | Task |
|---|---|---|---|
| 1 | The preflight decides "fast-forward available" from the local `master` ref, with no fetch. A commit on `origin/master` is invisible until the push fails, which is after the release has already committed VERSION and tagged. | `lib/release.sh` `release_ff_state` | T-3819 |
| 2 | The rollback is partial. It undoes `master` and the tag but leaves the VERSION-reconcile commit on the development branch. Any later ordinary push then publishes a release number with no release. | `lib/release.sh` push-failure branch (≈L355) | T-3820 |
| 3 | VERSION has two writers that disagree. The pre-push hook stamps it from `git describe` (`1.7.<commits>`) on every push. The release reconciles it to the tag (T-3242). After any push the tree disagrees with the commit, and the reconcile goes empty. | `agents/git/lib/hooks.sh` ≈L1251 versus `lib/release.sh` `release_reconcile_version` | T-3821 |
| 4 | Publishing is not atomic. The branch is pushed first, then the tag goes through a separate full structure audit. Consumers see and install the version on `master` while the command still reports it unfinished. | `lib/release.sh` tag-push loop | T-3822 |

## Why it matters

1. **A release number can exist without a release.** Had attempt 3 failed after the `master` push, consumers would have run a "1.8.0" that no tag names and no release note describes. Retracting it means force-pushing the install surface, a Tier 0 action that breaks every consumer that already fetched it.
2. **Status lies in both directions.** The release command said "not done" while consumers were already on it. Meanwhile VERSION on `bleeding-edge` said 1.8.0 while no release existed.
3. **Every future release hits cause 3** whenever a push and a release run back-to-back, which is the normal sequence.

## Contributing factors

1. **Process.** The agent ran "push, then release" in one background command. It then watched the tag rather than what consumers read (VERSION on master), and so misreported the state to the operator.
2. **The release-train invariant was broken from outside.** A peer agent committed directly to `master`. Only server-side branch protection can stop that (T-3818, operator: very high value).

## Prevention (per task)

1. **T-3819:** the preflight runs `git fetch <remote> master` and grades against `origin/master`.
2. **T-3820:** the reconcile commit is made only after the publish succeeds. If it must come first, the rollback reverts it.
3. **T-3821:** one writer for VERSION. Either the hook stops stamping the committed file (it stamps a generated, ignored file instead), or both writers use the tag rule.
4. **T-3822:** `git push --atomic <remote> master refs/tags/vX` (both refs or neither). A tag-only push skips the full structure audit.
5. **Regression test per cause**, using a fixture remote that holds a commit the local ref does not.
