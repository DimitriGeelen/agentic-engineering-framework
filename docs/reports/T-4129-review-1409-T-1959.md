# T-4129 — Review of 1409-sprind T-1959 (template arc + class YAML) against AEF as it works today

Reviewer: AEF framework repo. Scope: read-only review of `T-1959-durchgang-b.md`. All citations are in the AEF repo.
"Today in 1409" = doable with existing AEF features. "AEF change" = does not exist; one-line proposal only.

## Two facts to know first

- **AEF has no template-arc or arc-instantiation concept.** `tpl-arc-001`, `vorlage:`, `vorlage_version:` and the instantiator are your own
  layer. `lib/arc.sh` has no template handling. The arc fields it manages are `id/slug`, `anchor_task`, `headline_mechanic`, scoped
  drivers and status (`lib/arc.sh:445` marks `constituent_tasks` as deprecated; membership is derived from task `arc_id`).
- **AEF has no "## Ausrichtung" section.** I found no such section (or "Alignment") in `.tasks/templates/default.md` or
  `agents/task-create/`. The task template sections are Context, Acceptance Criteria, Verification, RCA, Evolution, Recommendation,
  Decisions, Updates (`.tasks/templates/default.md:56–319`). If your team added Ausrichtung, it is a 1409 convention, not a framework rule.

## Q1 — Where do template arc, commune arc and step tasks sit in the AEF rules?

**Finding.** Your I.5 instance is missing or violating five things AEF actually checks:

1. **`arc_id` absent, tag only.** The canonical link is the `arc_id:` frontmatter field. `check-arc-id` validates it on save
   (`agents/context/check-arc-id.py:19–29`: non-empty value must resolve to `.context/arcs/<slug>.yaml` or an `id:` match).
   The `arc:<slug>` tag is the legacy form. The Evolution gate accepts both (`update-task.sh:879`), but arc membership
   counting and the Watchtower arc pages are built on `arc_id` (`lib/arc_membership.py`).
2. **`## Verification` has only comments.** P-011 runs each non-comment line (`update-task.sh:1412`). A task with no commands
   passes through, so the gate checks nothing. That is the framework's documented backward-compat rule, not a bug on your side.
3. **Unfilled `{lauf}` and Human template text.** G-020 (`agents/context/check-active-task.sh:1138`) blocks source edits when ACs are
   framework placeholders like "[First criterion]". It does not know your `{lauf}` placeholders, so they pass. I hit this gate
   myself on this very task.
4. **Evolution.** The gate (`update-task.sh:854–915`) applies only to `build` tasks in an arc that already have an `## Evolution`
   section in the body. If the section is absent, the gate does nothing. Your instances omit it, so the gate is silently off.
5. **AC classes.** `### Human` boxes can only be ticked by the operator. The guard is `check-human-ac-tick`
   (`agents/context/check-human-ac-tick.py`), and audit FAILs on committed Human ticks without provenance (`lib/human_ac_ticks.py`).
   Leftover template text in `### Human` is a latent blocker (partial-complete, owner → human), not a harmless leftover.

**Reason.** The instantiator copies the class, not the framework's task contract.

**Proposal (1409 today).** Make the instantiator emit: `arc_id: kommune-<ags>` in frontmatter (not only the tag); concrete ACs with
all placeholders resolved at creation time (reject on a remaining `{…}`); a real `## Verification` command per step
(see Q2); an `## Evolution` section (so the gate is armed); and no `### Human` section unless a step really needs human judgment.
Where a step needs judgment, use `[REVIEW]`/`[REVIEWER]` with Steps/Expected/If-not (CLAUDE.md §Human AC Format).

## Q2 — Should tasks lead the run, or mirror the class with the log in run files?

**Finding.** AEF's gates only see the task file, so a task that stays `captured` while the run happens elsewhere is invisible to
the framework: no status, no verification, no episodic memory, no handover entry.

**Reason.** AEF's own answer to "two truths" is: the task carries the *result*, the heavy evidence lives elsewhere and is
referenced. Examples: research artifacts under `docs/reports/`, the bus (`fw bus post --blob`, size-gated at 2 KB, CLAUDE.md
§Result Ledger), evidence paths in ACs. There is no mechanism in AEF where an engine writes into task bodies.

**Proposal (1409 today).** Keep B6 as the log of record (run folders, collector, central file). The task gets exactly three things,
all written by the collector through `fw task update` (not by editing task text): (a) status `started-work` / `work-completed`;
(b) one `## Verification` line per step that *queries* the central file, e.g. `abfrage k6-pflichten ags=<ags>` or a check
script that exits non-zero if the latest finished run has no green evidence for that step; (c) an Updates line with the run id
and path. The ACs stay prose or checkboxes, the Verification lines are the machine truth. That way P-011 becomes the bridge:
close is refused unless the run files say so, with no second copy of the data. No AEF change needed.

## Q3 — "YAML is truth, tasks are generated" (B9) versus the task lifecycle

**Finding.** Compatible, but only with a clear split. AEF has no notion of generated versus maintained regions in a task, and
agents (and the framework: `update-task.sh`, handover, episodic) rewrite the file freely. Regeneration over a task would
overwrite Decisions/Updates/Evolution and ticks.

**Proposal (1409 today).** Draw the line by section:

| Generated once, then frozen per task (class-owned) | Maintained (task-owned, never regenerated) |
|---|---|
| frontmatter `name`, `arc_id`, `workflow_type`, `vorlage_version`; Context; the AC list (text); Verification lines | status, Updates, Decisions, Evolution, ticks, Recommendation |

Put the class version into the task (`vorlage_version`, you already have it for arcs). `nachziehen` must never rewrite an existing
task: for a changed class it creates a *new* task for the step (or appends a clearly marked "Class 3.0 delta" entry to Updates)
and leaves the old one to be closed or abandoned. Mark generated text with a one-line comment such as
`<!-- generated from kommunescan.yaml@3.0 -->` so a gleichlauf check can compare only that part. That also answers I.6.2: 60 new
tasks is the wrong default; archive stale arcs instead (D-Immutability: arcs are never deleted, `fw arc abandon` flips status
only, per the arc-005 headline in `.context/arcs/arc-grooming.yaml`).

## Q4 — Conformance check: project or framework?

**Finding.** Both, in order. AEF's audit has no template-arc concept: it checks YAML parse of `.context/arcs/`
(`agents/audit/audit.sh:1135–1170`), `anchor_task` resolution (`:1303–1331`), driver-reviewer records (`:4212`), stale-arc
warnings (`FW_STALE_ARC_DAYS`). Nothing compares an arc to a source of truth.

**Proposal.**
- *1409 today:* keep `instanziieren.py pruefe`, run it from `fw audit`'s pre-push path through your own hook, and also as one line
  in the `## Verification` of every class-change task. That is already the pattern used for cron and tool-set drift
  (CLAUDE.md §Verification Gate).
- *AEF change:* a generic "derived-artifact parity" audit hook: projects register `{source, derived_glob, check_command}` in a
  small YAML, `fw audit` runs the command and FAILs on non-zero. This is generic (cron registry, tool-set manifest and your class
  are the same shape) and avoids teaching AEF about "templates". Hand it over as a pickup to this repo; it will be scoped by
  inception, not built from the message.

## Q5 — B6 (status file + rename + one collector): weaknesses

AEF has no equivalent mechanism to compare, so this is an engineering opinion, not a framework fact.
1. **Crash between last write and rename.** `.laeuft` stays forever. Add a heartbeat (mtime or counter) and let the collector
   mark runs with a stale heartbeat `abgebrochen` itself, never delete them.
2. **Two runs of the same commune.** Key includes the run id, so files do not collide, but both can end `.fertig`. Define which
   wins (latest `.fertig` by start time) and have the collector record the superseded run as such. A lock file per commune also
   prevents the waste.
3. **Resume.** Make it a new run with `fortsetzung_von: <lauf>`, never an edit of a finished folder. Finished means immutable.
4. **Hash check only proves integrity, not completeness of the step.** Keep your "both directions" check, and add the expected file
   list per step from the class YAML.
5. **Collector is a single point.** Make it idempotent and re-runnable from scratch (you already say so); run it from cron and
   at the start of every Verification query.

## Q6 — What breaks first at 100+ communes

1. **Task and arc count.** 100 arcs × 12 tasks = 1,200 new task files. Task IDs, `.tasks/active/` scans in audit
   (`active-task-scan.py`) and Watchtower lists grow linearly; the arc pages already had an undercount bug at corpus scale
   (`lib/arc_membership.py:67–84`). Expect slow audits and noisy handovers before you expect correctness failures.
2. **Gate noise.** 1,200 `captured` tasks with empty Verification inflate "stale task" and handover sections.
3. **Shared learning files** (`nachweis.py`), the failure you already saw. B6 fixes the writes; also keep any shared file
   append-only or collector-owned.
4. **Dispatch cap.** AEF allows 5 concurrent TermLink workers per project (`TERMLINK_MAX_WORKERS`, raising is the operator's call),
   so "100 parallel" is really 5 at a time unless the operator raises it.
**Proposal (1409 today):** create commune arcs and tasks lazily (when a commune enters a cohort), not for the whole list up front;
give a commune one arc but only the *current* step's task open; `horizon: later` for the rest.

## Q7 — What makes success repeat, not happen once

1. **Close the loop through gates, not through prose.** Today the only machine-checked part of a commune task is nothing
   (empty Verification). Every step needs a Verification line that fails when the evidence is missing.
2. **One Änderungsregel.** Take the stricter (Kopf) one. Note that AEF itself records AC changes as a re-review trigger: the
   reviewer ledger digest covers the AC text, so an edited AC invalidates a prior verdict (CLAUDE.md §Human Task Completion Rule,
   `fw reviewer verdict digest`). Your "AC changed = structural" matches that.
3. **Use review, not stamps, for taste-like steps.** `fw task delegate T-XXX --dry-run` classifies each Human AC; deterministic
   ones become `[REVIEWER]` ACs, judgment ones go to a recorded independent verdict (`lib/verdict_ledger.py`, `lib/delegation.py`).
   For K10 ("Verbesserung zur Vorlage") use that path rather than an AC that someone just ticks.
4. **Record what each commune taught.** `fw context add-learning` per class change, and an Evolution entry in the step task.
   AEF's arc close requires a demo artefact showing the headline mechanic (`fw arc close --demo`), and arc closure is the human's.
   Your `k10_pflicht` should map to that: the Gemeinde-Arc's headline mechanic is the thing the demo must show.
5. **Measure against the reference set after every class change** (you do), and keep that number in the class-change task's
   Verification as a threshold check.

## The three most important changes

1. **Make the instance tasks real AEF tasks.** `arc_id` in frontmatter, no unresolved placeholders, an `## Evolution` section,
   no stray `### Human` template text, and at least one machine-checkable `## Verification` line per step that queries the
   central run file (Q1, Q2). This switches on P-011, the Evolution gate and arc membership at once. No AEF change.
2. **Split generated from maintained task text, and never regenerate an existing task.** Class-owned sections frozen with a
   version marker; task-owned sections untouched; class changes create new tasks or Updates deltas; stale arcs are
   abandoned, not rewritten (Q3). No AEF change.
3. **Run the YAML↔instance parity check as a Verification line and in the project's pre-push audit now, and propose a generic
   "derived-artifact parity" audit hook to AEF** (Q4). One rule (the stricter) for class changes (Q7).
