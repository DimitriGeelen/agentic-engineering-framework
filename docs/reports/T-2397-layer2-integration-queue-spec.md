# T-2397 — Layer 2 spec: serialized master integration queue (T-2394 G2)

**Status:** design spec
**Parent inception:** T-2394 (structural remediation: concurrent AEF agents on a shared backlog + master)
**Sibling layers:** L1 = T-2396 master-merge-only guard (SHIPPED); L3 = G4 disjoint write-sets (arc-011); L4 = G3 `fw task claim` lease (captured)
**Evidence base:** the 2026-06-14 manual consolidation (this session) — see §4.

---

## 1. Problem (what L1 does NOT solve)

T-2396 (Layer 1) makes one invariant structural: **no direct authored commit lands on master** — master advances only by FF/merge of a reviewed branch. That closes the "two agents both `git commit` on master" hole.

It does **not** supply the two things tonight's divergence actually needed:

1. **Serialization.** Nothing coordinates *which* branch FFs *when*. Tonight master diverged because two integration paths ran uncoordinated: a human hand-cherry-picked T-2377–2379 onto master while a worktree branch advanced 42 commits. L1 would have blocked neither (cherry-pick is now blocked by default in L1's design, but the *race* between two legitimate merges is the real gap). A merge that is "merge-only" can still collide with another merge-only merge. **The queue is what serializes them.**

2. **Un-partitionable file ownership.** The FF aborted on six files — `.context/audits/discoveries/LATEST.yaml`, `.context/project/metrics-history.yaml`, `.context/working/.hook-counter`, `.context/working/.loop-detect.json`, `.context/working/feedback-stream.yaml`, `.tasks/completed/T-2379-*.md`. These are generated/accumulated governance machine-state — the framework's `Cargo.lock`. They ride every branch because every session writes them into its own working copy, and they cannot be eyeball-merged. **L2 must regenerate or field-merge them, never `git merge` them.**

This is the CI/distributed-systems playbook: a **merge queue** with **lock-step integration** and **generated artefacts regenerated at the join, not merged**.

## 2. Scope

In scope (G2 only):
- A serialized integration verb (`fw consolidate` — name TBD, §7-Q1) that takes one reviewed branch and lands it on master.
- A single-writer lock so only one integration runs at a time (host-local; multi-host is L3/L4 + hub).
- A per-file-class strategy for the un-partitionable governance set.

Out of scope:
- Disjoint write-set enforcement before dispatch (L3 / arc-011 — `lib/write_set.py` + `orchestrator-graph.py pre-flight` exist but are not wired to a greenlight; that's a different gap).
- Task-claim leases (L4 / G3).
- Cross-host hub append-log (the design's full plane-split; L2 is the single-host minimum that the hub later generalizes).

## 3. Design

### 3.1 The verb

```
fw consolidate <branch> [--onto master] [--dry-run] [--demo <artefact>]
```

Algorithm (generalized from the manual dance in §4):

```
1. ACQUIRE integration lock (single-writer). Block/queue if held. (§3.3)
2. PRECHECK: master is ancestor of <branch>?  (clean FF eligible)
   - if not FF-able → attempt merge; on governance-file conflict go to step 4.
3. QUIESCE governance churn on the target checkout:
   - stash/snapshot the un-partitionable working-tree set (§3.2) — it is
     regenerable, so this is non-destructive.
4. INTEGRATE: git merge --ff-only <branch>  (or a real merge commit if diverged).
5. REGENERATE/MERGE the un-partitionable set per-class (§3.2) — do NOT git-merge them.
6. VENDOR: refresh .agentic-framework/ (prune node_modules/__pycache__ — see OBS-076).
7. VERIFY: master == expected tip; working tree clean; push gate green.
8. PUSH (optional, gated).
9. RELEASE lock. Emit a wire-evidence record (dispatch-style row) for the arc demo.
```

### 3.2 Un-partitionable file taxonomy + per-class strategy

Derived from the actual files that blocked tonight's FF. Each class gets a **merge strategy that is not `git merge`**:

| File / class | Nature | Strategy at integration |
|---|---|---|
| `.context/working/.hook-counter`, `.loop-detect.json` | monotonic counters / ephemeral | **regenerate** (take target-side or reset; never merge) |
| `.context/project/metrics-history.yaml` | append-only time series | **append-union** by timestamp key, dedupe |
| `.context/working/feedback-stream.yaml` | append-only event log (digest-keyed) | **append-union** by digest key (T-1985 auto-tick keys) |
| `.context/working/reviewer-overrides.yaml` | id-keyed list | **union by `id`** (the manual Python union I ran tonight) |
| `.context/audits/**/LATEST*.yaml`, `metrics-history` | regenerated by cron/audit | **regenerate** (next audit tick rewrites; take newest mtime) |
| `.tasks/**/T-*.md` (status/BVP churn) | semi-structured, multi-writer | **field-merge**: frontmatter status/horizon = last-writer-wins by `last_update`; body = branch (authoritative for the integrating work); reviewer-verdict block = newest scan-id. Conflicts on the *same field* → surface, don't auto-resolve. |
| `.context/episodic/T-*.yaml` | write-once at completion | **take-existing** (never overwrite a completed episodic) |

Principle (the Cargo.lock rule): **if a file is generated or accumulated, it is regenerated/unioned at the join — it is never a merge conflict.** A genuine *same-field, two-writer* task conflict is the only thing that should ever stop the queue and ask a human.

### 3.3 The lock (single-writer)

Minimum viable (single host, tonight's reality — one main checkout + N worktrees):
- A lockfile at the **git common dir** (`$(git rev-parse --git-common-dir)/fw-integration.lock`) so it is shared across all worktrees of the repo (OBS-075: coordination files are repo-global per git-toplevel).
- Contents: holder session id + epoch + branch. Stale-lock TTL (e.g. 10 min) with takeover logging.
- `fw consolidate` acquires before step 4, releases after step 9. A second integration blocks (or fails fast with "integration in progress by <id>").

Generalization path: swap the lockfile for a TermLink kv lease (`termlink kv set --lease`) when integration moves to the hub for multi-host (L4 substrate already proposes this).

## 4. Evidence from tonight (the proto-algorithm)

The manual consolidation *was* `fw consolidate` run by hand:
- **Serialization** = me confirming only one main session + the worktree were live, and pausing.
- **Quiesce** = `git -C MAIN stash push` of the regenerable churn (twice — the live session re-dirtied between FFs).
- **Integrate** = `git merge --ff-only worktree-arc012-continuous-run-s4s5` (clean, `4679b9a42..63d6a4781..74630cfd6`).
- **Field-merge** = during the earlier branch-side merge, I resolved `.tasks/completed/T-2379` by **field** (took OURS for status, theirs for episodics) and `reviewer-overrides.yaml` by **id-union** — exactly the §3.2 strategies, done manually.
- **Vendor** = `fw vendor self` + the OBS-076 node_modules FP that forced a Tier-2 bypass — L2's step 6 must prune so it never FP-blocks the queue.

Tonight is the existence proof that the algorithm works; L2 is its automation. The fact it took ~15 careful manual steps with two stash rounds and a bypass is the cost L2 removes.

## 5. Cautions surfaced this session (must inform the build)

- **OBS-076** — `_self_vendor_libs` find doesn't prune `node_modules`/`__pycache__` → phantom drift blocks pushes. L2 step 6 must prune; fix OBS-076 first or L2 inherits the FP.
- **Focus-drift gate reads main's `focus.yaml` from a worktree** (PROJECT_ROOT resolves to the main checkout). Governance *reads* already cross the worktree boundary — so L2's governance-file handling must be explicit about *which* checkout's `.context/` is canonical. This is also why the plane-split (governance state should be single-writer/hub-owned, not per-worktree) is the right end-state: it removes the "which copy is real" question entirely.

## 6. Minimal viable vs full

- **MVP (this slice):** `fw consolidate <branch>` for the single-host case — lockfile + FF + the §3.2 regenerate/union strategies for the 7 classes + pruned vendor + verify. No push (operator pushes), no hub.
- **Full (later):** merge-commit path for diverged branches; TermLink kv lease; hub-owned governance plane (governance writes never touch branches at all → §3.2 becomes mostly empty because there's nothing to merge).

## 7. Open questions (for the build task)

- **Q1 — verb name & home.** `fw consolidate` collides with the existing memory-consolidation verb (`agents/context/consolidate.py`). Use `fw integrate` or `fw merge-queue`? **Recommend `fw integrate`** (distinct, intention-revealing).
- **Q2 — task field-merge depth.** Is last-writer-wins on status/horizon enough, or do we need a 3-way field merge against the merge-base task file? MVP: last-writer-wins by `last_update`; revisit if it loses real edits.
- **Q3 — does L2 push, or only stage master for the operator?** Tonight push was operator-authorized but hit the vendor FP. Recommend L2 default `--no-push` (stage + verify), explicit `--push`.
- **Q4 — lock granularity.** Per-repo (one integration at a time) vs per-file-class. MVP: per-repo (simplest, correct).
