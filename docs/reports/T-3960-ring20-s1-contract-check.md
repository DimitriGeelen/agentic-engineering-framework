## What will bite you

1. **The hook layer fails open.** `fw hook <name>` exits **0** when the hook script is missing (`bin/fw:10272`). Both hooks exit 0 when the command cannot be extracted from the JSON (`check-tier0.sh:119-121`, `check-paid-backend.sh:39`). A crash exits with a code other than 0 or 2 (`lib/config.sh:172-181`). The supervisor must treat only `rc==0` with a well-formed payload as allow, and treat anything other than 0 or 2 as a refusal. It should also assert that the hook script exists before trusting rc 0.
2. **check-paid-backend judges the wrong task.** It reads `current_task:` from `focus.yaml` (`check-paid-backend.sh:40-46`), which is the interactive session's focus, not the commission's task. A paid-route approval is then checked against whatever the operator happens to be focused on. Either pass the task explicitly by calling `lib/review_cost.py check-command --task <commission task>` directly, or accept this as a residual.
3. **`parse_task_file` ≠ the P-011 gate.** Template-style task files put HTML comments and code fences inside `## Verification`. `parse_task_file` returns those lines as commands, which gives false reds. The missing pipefail gives the opposite: `cmd | grep -q` passes where P-011 can fail. Use `extract_verification_block` (`lib/verification-port.sh:202`, rc 2 = unreadable) and run each line with `bash -c 'set -o pipefail; …'` in the output tree.
4. **`orch/landing` will show in `fw doctor` / branch hygiene.** It is a long-lived `refs/heads/` branch with no task id. Merged into master, it reports `merged-undeleted orch/landing` permanently (`branch-hygiene.sh:281`). Brought over as a squash or cherry-pick, it is never an ancestor and eventually reports `behind-threshold`/`diverged-fork` (`:304-313`). Separately, AEF's secret-scan is a pre-commit hook, and a clean `git merge` fires `pre-merge-commit` instead (`hooks.sh:547-556`). Worker bytes therefore reach master unscanned unless the supervisor runs `agents/git/lib/secret-scan.sh` itself. If `PROTECT_MASTER=1` is set on ring20, "a normal commit" onto master must be a merge or a fast-forward.
5. **Rows without a terminal event stay "in flight".** If attempt rows never get a `terminal_event`, `_inflight_dispatch_status` (`resolver.py:1486`) holds them in flight until `FW_RESOLVER_INFLIGHT_MAX_AGE_MIN` and then reports them as stale anomalies. Every attempt row also counts toward the stall detector (`_stalled_task_ids`, `resolver.py:626`). Either write a terminal event yourself (under `keylock.guarding(DISPATCHES_LOG)`, since a bare append races `update_outcome_row`'s replace, see `spawn.py:228-240`) or accept the noise. Also export `PROJECT_ROOT` before importing `resolver`/`outcome`/`spawn`, because all three bind it at import.

## §4.11 — the `orch-approve` request

**Facts.**
- The action path has a closed verb set: `force-push`, `branch-delete`, `hard-reset`, `recursive-delete` (`tier0_action.py:57`; `action()` asserts membership, `:197`).
- There is exactly one pending-action file, `.context/working/.tier0-action.pending.json`. Every block overwrites it or deletes it (`check-tier0.sh:883-886`). `fw tier0 approve` approves whatever is in it and then removes it (`tier0_action.py:833-838`).
- There is one legacy pending-hash file (`.context/working/.tier0-approval.pending`, `check-tier0.sh:63,880`). Watchtower cards, by contrast, are one file per command hash, so several can coexist.
- The module refuses under `CLAUDECODE=1` unless `--i-am-human` is given, and then records `approved_by: agent-override` (`:825-830`). CLAUDE.md states that a same-user agent can forge approval records.
- The grant TTL is 300 s (`TIER0_APPROVAL_TTL`). Push approvals carry a second clock, the 60 s admit TTL (`:63`).

**Options.**
- **A. Keep ring20's root-only approval files plus an ntfy post per consumption (as specified).** No AEF change, and it is stronger than AEF on worker separation (root-only dir). It is still an operator-only verb with no AEF audit trail, and it lives outside `fw audit`.
- **B. Use AEF exact-text approval today.** The supervisor runs the override through a deterministic command string that embeds `<commission_hash> <gate>`, blocks through `check-tier0` with a pattern that matches it, and the operator approves the **Watchtower per-hash card**. This works now, avoids the single CLI slot, and leaves an audit trail in `.context/bypass-log.yaml`. The costs: it needs a check-tier0 pattern that recognises the orch override command (a governance change to the detector), `fw tier0 approve` on the CLI still races the single slot, and the approval binds text rather than structured targets.
- **C. Add `orch-approve {hash, gate}` as a fifth action verb with keyed pending entries.** This is the cleanest binding and matches the round-7 rule "no key is normalised". It is also a change to AEF's Tier-0 grammar and pending model, which has been through 7 hardening rounds. Making the pending slot multi-entry affects every verb, not only this one.

**Agent's advice to the AEF operator (advisory only, your call):** ship **A** now, as ring20 already plans. If AEF wants an upstream answer, scope **C** as an inception and record "single pending slot" as an observation in its own right, because the clobbering also affects interactive sessions and not just the orchestrator. B is a workable bridge only if the operator accepts a detector pattern for orch commands.
