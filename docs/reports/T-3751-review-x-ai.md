VERDICT: ADOPT-WITH-CHANGES — keep function+instance only for agents (and pid vs checkout as disambiguation); do not respawn from inbound mail, and do not make every level an actor.

Q1. Position: the uniform two-label grid is the wrong abstraction; only the agent level truly has both a role and a live instance.
Host: drop the instance label from identity. FQDN is the durable name (§2 D2); IP is a DNS result with a TTL, not a second identity. Putting IP beside FQDN will split one host into two addresses the moment DHCP or a tunnel moves, and senders will “climb” to a stale address that still looks well-formed.
Hub: merge to one label until multi-hub is a real decision. D6 already says hub is 1:1 with host and `hub=` is optional. A hub name plus a hub id, with “maybe hub1..n or one hub per project” still open (§4.1), freezes an undecided topology into the wire grammar. Human hub names can be display-only.
Project: keep `pid-…` as the only routing identity (already ruled, §2, 2026-10-03). A project instance id is justified only as a checkout disambiguator when two working trees share one pid (§7.3). It must not make the project an active, respawnable actor. D2 says the project is passive — a location, never callable. “Spin up a new project instance that continues from saved context” (§4.2) has no defined directory, git rev, or vendor session. That is a new ontology, not a label.
Session: drop the function label. Sessions are conversations or dispatched workers (§7.1), not roles. A “session name” you can respawn-by will treat a dead interactive terminal and a dead `claude -p` worker as the same function. Keep the TermLink instance id. An optional class tag (`interactive` | `worker`) may live in metadata for preference, not in the address.
Agent: keep both. `@research` is the function; the instance id is the live actor. That is D1 done cleanly, and it matches D7’s single-writer claim. Do not add vendor or model to the address: §5 requires cross-vendor operation, and Portability forbids locking a correspondent to Claude. Missing, and more important than another label: a receipt semantic (stored vs handed over vs replied) and a liveness bit that is not “present in the registry”.

Q2. Position: the wire address stays a short named tuple; new labels do not become new path slots.
On the wire, for routing: host FQDN, optional hub id, project pid, `@agent`, and an agent instance id only when the sender demands that actor (sticky). That is enough to deliver or to queue.
Metadata, not routing equality: project checkout id, session instance id, session class, vendor/model, circuit id, last-seen IP. Display only: folder name, human project name, hub nickname, session title, IP. IW-3 (`--to 832-Workflow-designer`) is a resolver in front of the address, not a second project slot.
The path form is already inconsistent with V9 (basename vs full path, §2 D3). Consumers on older framework versions must keep working (§5). Positional `//host/hub/project/session/agent` cannot grow a project-instance or session-name segment without breaking parsers. Named fields, unknown fields ignored. One grammar, agreed with TermLink before they key wake-up on it (their T-3325, §5).

Q3. Position: fallback may retarget only inside the same pid and the same `@name`, and it may queue; it may not spawn, and it may not upgrade a receipt.
From “full address does not resolve”:
1. Require pid + `@agent`. If either is missing, bounce `INVALID_ADDRESS`. Do not infer the project from a folder name.
2. Resolve FQDN. Failure → `HOST_UNREACHABLE`. Do not substitute a cached IP. Do not pick another host.
3. Resolve the hub on that host. If it will not accept a write, bounce `HUB_UNREACHABLE` or show sender-local `QUEUED_LOCAL`. Never emit `HUB_ACCEPTED` for a write that did not land. Stop. Do not climb to a different hub.
4. Resolve pid. Unknown → `UNKNOWN_PROJECT`. Never another project (agreed, §4.3). Never create a checkout.
5. Liveness is a probe (R7), not a registry row. Orphans must not count as alive (§3.8). If a sticky instance id was given and the probe fails, return `INSTANCE_DEAD` and do not retarget if the sender set exact-instance. If sticky was a preference: choose at most one live receiver of the same `@name` in the same pid that holds the consumer lease and whose ready flag is that session’s (§3.4). Inject there. `RECEIVED` only after the receiver stores; `HANDED_OVER` only from transcript evidence, credited to that session id.
6. If none is live: append to a durable mailbox keyed by `(hub, pid, @name)`, receipt `INBOX_STORED`. That receipt means “bytes retained”, not “the agent has it”. If no `HANDED_OVER` within a declared bound, emit `PICKUP_OVERDUE`. Nudges dedupe on `client_msg_id`.
7. Respawn, if ever, is a separate supervisor action (Q4). Its receipt is `RESPAWN_STARTED`, which is not delivery. Delivery still waits for step 5.
Stop rules: no cross-project, no cross-host, no cross-`@name` (“any agent in the project”), no session-name match, no treating hub accept as handover. Sender-visible states are only `INVALID_ADDRESS`, `HOST_UNREACHABLE`, `HUB_UNREACHABLE` / `QUEUED_LOCAL`, `UNKNOWN_PROJECT`, `INSTANCE_DEAD`, `INBOX_STORED`, `PICKUP_OVERDUE`, `RECEIVED`, `HANDED_OVER`, `REPLIED`, and optionally `RESPAWN_STARTED`. `REPLIED` requires `in-reply-to` that `client_msg_id` (§3.2). Escalation keys off missing `HANDED_OVER`/`REPLIED`, not off a quiet hub.

Q4. Position: an inbound message must not start a paid agent or a project instance; D5 does not authorize that.
D5 pre-authorizes a parent to re-provision its own missing child (Tier-3 self-heal, §2). It does not authorize any peer to spend the operator’s money. The constitutional rule is that nothing gets done without a task, and Tier-0/spend stays with the human (§1.1, §5). “Ingest the context and follow up on the message” (§4.2) makes the foreign payload the task. That is an open relay for spend.
Concrete policy: default `respawn: never` per `@name`. A supervisor that itself launched a worker may restart that worker under an intensity cap (N restarts per hour), loading saved context plus a pointer to the mailbox — the message is data, not a spawn command. Cold start, first use of a name, and any spawn caused by mail from another project require the operator, or an explicit opt-in budget in the committed project config. The project owner pays, never the sender. Rate-limit per pid, cap concurrent instances, cooldown after failed boot. Mistaken or hostile mail bounces or queues; it does not boot a model. A hung agent is `SUSPECT` after failed probes: stop injecting, do not spawn, until death is proved or the supervisor decides. D4’s “invalidate only on positive proof of death” (§2) otherwise leaves orphans looking live forever (§3.8) and blocks both fallback and a legitimate restart.

Q5. Position: one consumer lease per `(pid, @name)`; at-least-once delivery with idempotency, not a claim of exactly-once.
Two live `research` agents must not both take the message and both run up a bill. Fan-out is the wrong default (SIP-style forking). The mailbox is per function, not per instance. One session holds a lease, same idea as the session-keyed ready flag that fixed §3.4, and same family as D7’s single-writer claim — extended to reads. Only the lease holder is injected and only that session may emit `HANDED_OVER`. Lease expiry on probe failure lets the other instance take the still-unacked message. Dedupe on `client_msg_id` so nudges do not become new work.
Two checkouts sharing `pid-…` on one host: the checkout id breaks the tie only by claim, not by spawning a third tree. The non-holder gets `CONFLICT` if it tries to consume. A fork that forgot to mint a new pid (T-3534, §2) will silently eat the other clone’s mail — treat unexpected second checkout as a conflict, not as capacity.
Exactly-once across a crash is not available. Say at-least-once plus idempotent side effects. A design that promises exactly-once will hide duplicates.

Q6. Position: this model prevents almost none of §3 unless the receipt ladder is mandatory; applied naively it adds new lying levels.
Incident 1 (no receipt on the hub path) and incident 7 (`send-file` ok ≠ delivered) are fixed only by Q3’s named receipts and `PICKUP_OVERDUE`, not by labels. Incident 2 (replies not bound to `client_msg_id`) is untouched; the label scheme never mentions it, so nudging still never stops. Incident 3 (hub receipt, no wake consumer) remains if `INBOX_STORED` or “function matched” is shown to the fleet cockpit as health. Incident 4 returns if “session is a preference” (§4.2) is implemented as “whichever session of this project prompts next”. Incident 5 is TermLink’s shared signing identity; AEF labels do not fix wake-up until both sides key on `@name` plus instance and authenticate the sender. Incident 6 (258 posts, one reader) is what a function mailbox becomes with no overdue signal. Incident 8 gets worse if a registry row counts as the instance label being alive. Incident 9 (median 49 min) is not a naming problem; a respawn is slower than a 30 s tick, not faster.
New class of the same bug: `RESPAWN_STARTED` or “matched function `research`” reported as success while the new process never reads the payload; a session title match injects into the wrong conversation and `HANDED_OVER` is true for the label and false for the intended thread; a second checkout of the same pid answers for the first. More levels means more places a state can be true at the wrong one — the pattern §3 already names.

Q7. Position: copy supervision and address-of-record vs contact; do not copy “a message activates an actor”.
Erlang/OTP: registered name vs pid, and a supervisor with a restart intensity. A `call` to an unregistered name fails; it does not spawn. Copy that. The sender is not the supervisor.
Kubernetes: a Service does not create Pods; a Deployment does, from spec, not from a packet. Copy that split. An HPA does not scale because a stranger sent a request.
XMPP/SIP: bare JID (address of record) vs full JID (one binding), registration with expiry. Copy that for agents only, and copy expiry so orphans die. Do not copy SIP parallel forking.
Email: SMTP accept is not user delivery; a DSN is delayed and explicit. Copy DSN semantics. An open relay — anyone can cause you to accept and act — is what foreign-triggered respawn is. Avoid it.
DNS: name vs address record. Copy FQDN-as-identity, IP-as-cached record. Do not put the A record in the durable address.
Akka: actor ref vs path, death watch, at-most-once default, explicit routers. Copy death watch and “unbounded create-from-message is a mailbox bomb”.
Orleans virtual actors are the closest temptation and the one to refuse. Grains activate on a message only because the runtime also has single activation, placement, and cheap methods. An LLM turn is not a grain call. Duplicate activation there becomes duplicate spend here.
The climb in `lib/aef_address.py` (§2) is a resolution ladder, like walking a supervisor tree to find who can help. It is not a spawn ladder. The sidecar already stops at the project inbox (`lib/sidecar/circuit.py`); that inbox is where receipts go to die today. Fix the inbox contract before adding rungs.

Q8. Position: adopt with the changes above; the single reason is that message-triggered respawn confuses a routing name with the authority to spend and to act.
Adopt: `@agent` plus instance id; pid as the project key; sticky-then-leased-equivalent-then-inbox; receipts that cannot be upgraded; no cross-project fallback; joint grammar with TermLink.
Change: no IP, hub nickname, session name, or vendor on the wire; checkout id is a conflict key, not a respawn target; respawn is supervisor policy with intensity limits, default off; probe beats registry; `client_msg_id` binds every receipt and every reply; task gate still applies to whatever boots.
Rejecting the whole note would throw away the one distinction D1 still lacks (role beside instance). Adopting it as written would institutionalize the §3 failure mode one level higher and add an open spend relay.

TOP 3 RISKS:
1. Spend relay. A peer (or a compromised 832 session) posts a burst at `@research` on 999-AEF while AEF’s receiver is down, as on 2026-10-03. Each message is read as “instance dead → spin up `research` and follow up”. The operator pays for N model sessions whose task is an untrusted payload, and the framework’s own “nothing without a task” rule never runs because the mail was the task.
2. Lying receipt, new rung. Fallback reports `RESPAWN_STARTED` or function-level accept. The new process fails to find context (§7.4) or has no wake consumer (§3.3). 055’s cockpit shows AEF responsive; the sender stops nudging; the mailbox repeats the retired `framework:pickup` pile (§3.6). True at function level, false at the agent.
3. Wrong live target. Two checkouts share `pid-…`, or an orphan receiver still sits in the registry (§3.8), or a session title matches another conversation. Delivery or respawn attaches to the wrong instance; `HANDED_OVER` is credited there (the §3.4 bug, via labels). D4 refuses to invalidate the orphan without positive death, so the real agent never sees the message and a divergent checkout may answer it.

WHERE I DISAGREE WITH THE AGENT'S READING (§4.3, §7):
- §4.2 is not “D1+D5 applied”. D1 says climb and open a new circuit to a working equivalent. D5 says the parent may re-provision a child it already owned. Neither says a foreign message starts a paid agent, nor that a project checkout is spawned from mail.
- Adding a project instance id and calling the project callable is not a refinement of D2. It revokes “project is passive”.
- A session name is not the same kind of function as `@agent`. Symmetry across five levels is the mistake, not a clarification.
- “The receipt names the level that took the message” is necessary and not sufficient. The sender was burned by the right level saying the wrong thing (`HUB_ACCEPTED`, “delivered”). Receipts must name the semantic, bound to `client_msg_id`.
- §7.2 is not an open tension to note later. It is a blocker. Default is do not spawn.
- §7.4: a conversation thread on disk is not a safe resume image, and “follow up” skips the task gate. Prefer queue-until-alive over ingest-and-act.
- §7.5: IP is never an address component. Resolution cache only.
- Also missed: D4 plus orphans blocks both honest fallback and restart; TermLink T-3325 can freeze the current grammar before this one is agreed; old consumers will still treat hub accept as success during migration, so the receipt protocol needs a version, not just new labels.
