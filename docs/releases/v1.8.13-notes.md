# v1.8.13 — security hotfix

v1.8.13 is v1.8.12 plus seven fixes to the framework's command classification: the read-only allowlist that lets an
agent run plain reads without an active task, and the project-boundary read check.

- **Five close ways a command could pass as a read** while it wrote a file, ran in another repository, or read outside
  the project: T-4367, T-4395, T-4408, T-4409 and T-4396.
- **Two only relax the allowlist** for subcommands that are genuinely read-only: T-4368 and T-4422.

Nothing else changed. If you are on v1.8.12, upgrade.

## Fixes

**T-4367: `git diff/log/show/diff-tree/diff-index/whatchanged --output=FILE` is a write.** In v1.8.12 these passed as
reads, although `--output` writes the file. They are now treated as writes, both by the allowlist and by the shell
write scanner.

**T-4408: git's repository-selecting environment variables are only read-only inside the project.**
- In v1.8.12, `GIT_DIR=/other/.git git log` and the `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE` and
  `GIT_OBJECT_DIRECTORY` forms passed as reads, and so did a variable set with `env VAR=` or `export VAR=; git ...`.
  A repository's own configuration can run commands, so a "read" there can execute code.
- These are now read-only only when the value resolves inside the project.
- `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT` with `KEY`/`VALUE`, `GIT_CONFIG_GLOBAL`, `GIT_EXEC_PATH` and
  `GIT_ALTERNATE_OBJECT_DIRECTORIES` are refused.
- Also refused: `..` escapes, a prefix lookalike (`<project>-evil`), and the variable behind `exec`, `command`, `nice`
  or `timeout`.

**T-4409: git is judged by the directory it actually runs in.**
- In v1.8.12, `cd /tmp/evil && git status` passed as a read, running git in another repository.
- The classifier now tracks the working directory through `cd`, `pushd`, subshells, groups, `cd -`, `cd ~`,
  `CDPATH` and `$HOME`/`$OLDPWD`. It refuses when the directory is outside the project, or when it cannot know the
  directory.
- `cd <project>/docs && git status` stays a read.
- **One behaviour change:** `cd X || git status` is now refused. It is over-strict but not a hole: git runs in the
  original directory or not at all.

**T-4395: the boundary read check judges paths under top-level directories it does not know.** In v1.8.12, a read
such as `cat /mnt-share/...` or `grep -r` in a top-level directory outside the framework's known list was allowed.
It is now judged like any other outside path. Paths inside the project, regex words and nonexistent top-level names
are unaffected.

**T-4396: read-only loops pass the allowlist.** `for f in *.py; do head -1 "$f"; done` and
`while read -r l; do echo "$l"; done` are now reads. This fix is required by T-4409, which tracks the working
directory inside them. A loop whose body writes, redirects, uses `cd` or `if`, or runs git outside the project is
still refused.

**T-4368 and T-4422: read-only git subcommands no longer need a task.** `git check-attr`, `git check-ref-format`,
`git diff-index` (without `--output`) and `git version` are reads. `git --version` is unchanged.

## How it was tested

- **Regression tests:** five new bats files fail 57 cases against v1.8.12 code and pass on v1.8.13:
  - `t4367_git_output_option` (6 of 10)
  - `t4395_boundary_unknown_top_reads` (8/20)
  - `t4408_git_env_repo_boundary` (17/25)
  - `t4409_git_cwd_repo_boundary` (17/28)
  - `t4396_safe_commands_loops` (9/27)

  T-4368 and T-4422 were probed directly.
- **Field tests, from other projects:** every fix has at least one positive field test; T-4395, T-4408 and T-4409
  have two.
  - ring20-dashboard ran 58 cases with v1.8.12 as control.
  - dimitri-mint-dev ran a fresh container per version.

  Evidence: `docs/reports/field-test-v1.8.13-results.md`.
- **Full unit suite, v1.8.13 vs v1.8.12** (same host, same start time): **0 failures attributed to the hotfix.** Every
  hotfix-only red was re-run alone on both versions and traced:
  - Some were older tests that asked about git without saying where it runs. These were fixed by giving them a known
    directory (T-4429), not by changing the product.
  - The rest were load flakes, failures already present in v1.8.12, or interference between the two parallel runs.

  Evidence: `docs/reports/T-4420-hotfix-v1813.md`.

## Why it was released

Under the standing release rule, a release ships to master without asking when every fix in it has a positive field
test from another project, and the release's own gates are green. v1.8.13 meets both. The release decision is
recorded in `.context/releases/decisions.jsonl` (`v1.8.13`, by field-evidence).

## Upgrading

```
cd /path/to/your/project && .agentic-framework/bin/fw upgrade
```

If a command an agent used to run without a task is now refused, read the refusal: it names the reason (outside the
project, unknown working directory, or a write). Run it from inside the project, or under a task.
