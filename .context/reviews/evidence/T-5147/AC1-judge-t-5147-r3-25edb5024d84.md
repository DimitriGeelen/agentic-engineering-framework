# T-5147 Human AC#1: evidence (reviewer judge-t-5147-r3-25edb5024d84, revision dd7b0f7f8)

Criterion: both reloads after a recorded verdict are as quick as usual; a task whose verdict
just turned green appears as ready by the second reload (about 20 s later) at the latest; no
task shows as ready that is not.

## What I checked

1. **Code** (`web/shared.py` 1890-2020 at the reviewed revision; `git diff dd7b0f7f8` on the
   file and its test is empty). `review_readiness(allow_stale=True)` returns a cached entry
   whose stamp moved only when the task file is unchanged AND the cached state is not READY,
   and queues the task for one daemon thread `readiness-refresh`. A cached READY falls through
   to an inline recompute. Only `board_awaiting_reason` passes `allow_stale=True`.
2. **Tests**: `python3 -m pytest tests/web/test_t5147_readiness_stale_while_refresh.py` gives 5 passed.
3. **Live server**: `bin/fw watchtower current` says pid 237655 is newer than every file under
   `web/`. Three `GET http://192.168.10.107:3000/tasks`: 1.04 s, 0.93 s, 0.84 s (HTTP 200,
   1.15 MB); `?view=list` 1.81 s. Machine load average was about 90 during all measurements.
4. **A live ledger write could not be observed.** I watched every `.context/reviews/*.jsonl`
   mtime for 4 minutes (19:03:39-19:07:39); none moved. I am not allowed to write a ledger
   file other than through my own verdict, so steps 2-3 of the criterion were not run against
   the live page.
5. **Simulation in a separate process on the real task files** (917 active, 445 awaiting,
   54 ready). The ledger stamp was moved in memory only (`_readiness_stamp` wrapped; nothing
   on disk touched), then the board's own call (`task_review_state(p, allow_stale=True)`) was
   run for every active task:

   | pass | time |
   |------|------|
   | warm, no ledger write | 0.42 s |
   | first pass after the simulated ledger write (board path) | 0.61 s |
   | same pass through the exact path (the old behaviour) | 119.1 s |
   | background refresh, 390 tasks queued, until the queue was empty | 99.6 s |

   - States served right after the write were identical to the states before it.
   - Tasks served READY that the exact path does not call ready: 0.
   - After the refresh finished, board states equalled the exact states for all 917 tasks.
   - A 40-task profile gave 0.027 s per exact recompute, so the cost per task varies a lot;
     the full queue averaged 0.26 s per task under this load.

## Findings

- **Reloads as quick as usual: met.** 0.61 s against 0.42 s warm, where the old path took 119 s
  in the same process.
- **No task shows as ready that is not: met.** By construction (a READY is never served stale),
  by the tests, and 0 mismatches in the simulation.
- **Ready by the second reload about 20 s later: not shown, and my measurement contradicts it.**
  The catch-up is the same recompute as before, moved to one background thread that starts at
  the first board load after the write. It took 99.6 s here. The task file itself puts the
  same work at 9-22 s on a quiet machine, so even then the upper end is past 20 s. The queue
  is popped in arbitrary order (`dict.popitem`), so the task that just turned green has no
  priority. The task's own tests and measurements time the reloads; none shows a task
  turning ready within 20 s.
- The stamp also contains the git generation, and `verdict record --commit` both writes the
  ledger and commits, so one recorded verdict moves the stamp twice; a board load between the
  two queues the refresh again. The state still converges (the refresh stores the new state),
  but this lengthens the catch-up further.
