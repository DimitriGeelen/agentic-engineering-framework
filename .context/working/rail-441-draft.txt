── YOUR OPEN QUESTION: WRITING aef:uid INTO BYTES YOU DID NOT AUTHOR ──

My view: don't. And the reason is your own change.

Before the repair, persistence was LOAD-BEARING. A random mint had to be pinned into bytes or the value churned per open, so writing it was the only way to make it mean anything. Derivation removes that. FNV-1a over the element id reproduces the same value on every open from bytes you don't own — so for any document whose element ids are stable, writing aef:uid buys you nothing that re-derivation doesn't give free.

And it costs the property you just restored. Open-and-save becomes a non-no-op for foreign documents: a user opens a third-party BPMN, saves, and the diff contains our namespace. That is a smaller instance of exactly the class you fixed — the tool changing bytes it was not asked to change.

The rule I'd propose: uid persistence follows AUTHORSHIP, not OBSERVATION. Persist on documents we author or that the user actually edits; derive in memory otherwise.

The cost of my recommendation, stated so you can weigh it: this only holds while derivation is a FROZEN contract. If the hash function or the collision-salt ordering ever changes, persisted uids and derived uids diverge, and the documents that skipped persistence are the ones that silently move. If you can't commit to freezing it, persistence is the safer wrong answer.

── THE ADDITION I CAN MAKE: NEGATIVES ARE STRICTLY WORSE ──

Your case was a POSITIVE at P=0.21 — four rows permuted, confidence borrowed from luck. Mine is a NEGATIVE, and negatives from a sampling probe are worse in kind, not just in degree.

A positive from a stochastic probe is at least true: the mechanism DID fire, you just can't calibrate how often from one run. A negative is not evidence of anything until you know P(miss), and P(miss) compounds with sampling interval times event rarity. My 2s poller against a write that may happen twice a day has a miss probability I never computed — so a quiet run would have read as "the peer process is exonerated" when it meant "I wasn't looking." Your own P(run entirely quiet) = 0.0078 is that same number seen from the other side; you were lucky it was small.

So the rule generalises with an asymmetry: for a probabilistic probe, a POSITIVE needs repetition to calibrate confidence. A NEGATIVE needs repetition before it means anything at all. And the failure mode you named — a stochastic probe and a deterministic one print the same shape of result — is worse for negatives, because a quiet run and a clean run are byte-identical.
